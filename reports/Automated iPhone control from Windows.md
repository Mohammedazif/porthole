# Replace dead reckoning with absolute HID pointing

The most promising way to make Porthole control an iPhone exactly and with almost no manual setup is to keep the current architecture and change two things: the mouse and the setup step. Porthole's Bluetooth LE HID peripheral should send a **16-bit absolute Generic Desktop mouse (X/Y 0..32767)** instead of relative deltas, and Porthole should turn AssistiveTouch on from the PC over a trusted USB pairing using the **lockdown `AssistiveTouchEnabledByiTunes` key**, which needs no Developer Mode. On iOS 27 the absolute mouse maps straight to screen fractions under AssistiveTouch. It needs no calibration, it landed 10 of 10 taps within 0.001 of the target over USB, and it was confirmed over BLE HOGP. That removes both dead reckoning and the need to find a translucent pointer over playing video. The uncertainty is iOS 26.6.1. **No source has tested an absolute mouse on iOS 26**, and reports from 2020 (iOS 13/14) say absolute BLE mice did not move the pointer. A one-day spike on the user's phone therefore decides the whole plan. If the spike fails, Windows has two fallbacks on 26.6.1: the existing relative-plus-vision controller, or WebDriverAgent for exact discrete taps at about 0.6–0.9 s each. The cleaner option is to update the phone to iOS 27, which adds the confirmed absolute HID path and Apple's new **CoreDevice universal HID service**, which takes absolute multi-touch with no AssistiveTouch at all. In every architecture the user still has a few one-time steps: tapping "Trust" over USB once, starting the Bluetooth pairing from the iPhone, and on iOS 27 enabling Developer Mode if they want the CoreDevice path. Nothing found makes the phone side fully zero-touch.

## An absolute mouse descriptor is the single decisive experiment

Porthole's report map today declares report 2 as an 8-button mouse with 16-bit signed **relative** X/Y (`Input 0x81 0x06`). The controller then has to anchor in a corner, model iOS acceleration, and close the loop by finding the AssistiveTouch dot in the decoded mirror ([src/hid/hid_reports.c](../src/hid/hid_reports.c); [PLAN.md §4.4](../PLAN.md)). That loop works on static screens: spike S3 hit Calculator keys within 2–8 px on iOS 26.6.1. It is also the part that breaks when the dot sits over moving video, because no setting turns off iOS pointer acceleration and nobody has published its curve. Users on iPadOS 26 still complain about forced acceleration, with no fix from Apple ([Apple Community 256142488](https://communities.apple.com/de/thread/256142488); [Apple Discussions 256240307](https://discussions.apple.com/thread/256240307)). Commercial products that use the same AirPlay-plus-BLE-HID design work around it by telling users to set Tracking Speed to 6 and hide the PC cursor "for more accurate clicks". That shows they never solved positioning ([Apowersoft FAQ](https://d2t95nfi15v50s.cloudfront.net/faq/how-to-control-ios.html); [iMyFone MirrorTo FAQ](https://www.imyfone.com/support/imyfone-mirrorto/)).

The new evidence comes from the esp32-iphone-agent family of projects, from late October and early November 2026. A spike firmware tested four descriptors on an iPhone 17 Pro running iOS 27. Each was tested alone in the report map: a Digitizer touch screen, a multi-touch screen, a pen, and a Generic Desktop mouse with absolute X/Y. **The touch screen, multi-touch and pen descriptors produced nothing. The absolute mouse "works, delivered as `touch`" with AssistiveTouch on**, and ten taps over two loops all landed within 0.001 of the target ([abs-touch spike README](https://github.com/chenshaorong0118/esp32-iphone-agent-ble/tree/spike/abs-touch/spikes/abs-touch); [issue #98](https://github.com/onehumanbeing/esp32-iphone-agent/issues/98)). The working descriptor is plain: Generic Desktop / Mouse / Pointer, 3 buttons plus padding, X and Y each 16 bits with Logical and Physical Min/Max 0..0x7FFF flagged `Input (Data, Var, Abs)`, and a relative 8-bit wheel. Its author notes that "iOS maps X/Y straight to screen fractions while AssistiveTouch is on, so no homing or calibration" ([abs_mouse.h](https://github.com/onehumanbeing/esp32-iphone-agent/blob/main/hardware/hid_bridge/abs_mouse.h)). Most importantly for Porthole, a BLE HOGP build was tested on 2026-10-27. It used one 0x1812 service with keyboard, absolute mouse and consumer reports, which is the same layout as Porthole's. It reported that "`at x y` lands where it should without calibration, `click` opens the tapped icon" ([jinwon-int/esp32-iphone-agent #104](https://github.com/jinwon-int/esp32-iphone-agent/issues/104); [ble_hid.h](https://github.com/jinwon-int/esp32-iphone-agent/blob/main/hardware/hid_bridge/ble_hid.h)). In the same project's small benchmark, a single click took a median of **0.46 s with the absolute mouse versus 1.02 s with the relative mouse**, and the worst case fell from 4.95 s to 0.56 s ([PR #99](https://github.com/onehumanbeing/esp32-iphone-agent/pull/99)). Those times include an agent loop, so they compare the two designs rather than measure raw HID latency.

The evidence against this approach is older but real. In 2020, an nRF52 BLE mouse on an iPad running iOS 13 "stopped moving" when its input flag was switched to Absolute, and another developer confirmed the same behaviour ([Apple Developer Forums 652700](https://developer.apple.com/forums/thread/652700)). An Arduino USB absolute mouse failed on iOS 14 ([NicoHood/HID #123](https://github.com/NicoHood/HID/issues/123)). Those failures involved iPads, older iOS versions, and in one case a descriptor that only flipped the Abs bit on an 8-bit signed range. None of those match a 2026 iPhone with a clean 0..32767 range. The sources cannot say whether absolute support arrived in iOS 27 or earlier, and the BLE test in #104 did not state its iOS version. The likeliest reading is that any iOS version from 26 on accepts the clean descriptor, but that is a hypothesis, and it is the one thing Porthole has to test on the user's 26.6.1 phone before committing.

Three implementation quirks are already documented and should go into Porthole's controller from the start. First, **"iOS ignores X/Y in a report that changes a button."** A tap must therefore be a position-only report, then a short settle (the firmware uses 60 ms), then press, then release ([PR #99](https://github.com/onehumanbeing/esp32-iphone-agent/pull/99)). Second, a large jump while the button is held reads as a flick: "a jump is a flick to iOS, and the list flies". Synthesized drags must glide in small steps, about 245/32767 per 8 ms report, while a Home or Back flick must be fast, about 0.1 s, or it opens the App Switcher instead ([abs_mouse.h](https://github.com/onehumanbeing/esp32-iphone-agent/blob/main/hardware/hid_bridge/abs_mouse.h)). For Porthole's live "follow the PC mouse" mode, this works in Porthole's favour. Forwarding the PC cursor's normalized window position at the native report rate turns a fast PC drag into a fast iOS flick, much as a finger would. Third, scrolling through the wheel usage is unconfirmed: the event arrived at the right spot with deltaY 0. Scrolling should therefore default to held-button drags until it is tested.

## Two of three phone-side setup steps can be removed from the PC

AssistiveTouch stays mandatory on iPhone. Apple's procedure says "With your pointer connected, turn on AssistiveTouch", and iPhone has no native pointer support of the kind iPadOS has under Pointer Control ([Apple Support 111775](https://support.apple.com/en-us/111775)). The iOS 27 spike also saw nothing with AssistiveTouch off, though its author marks that result unconfirmed ([abs-touch README](https://github.com/chenshaorong0118/esp32-iphone-agent-ble/tree/spike/abs-touch/spikes/abs-touch)). The question is therefore whether the PC can turn AssistiveTouch on, and there is a good answer. **pymobiledevice3's `lockdown assistive-touch on` and go-ios's `ios assistivetouch enable` both write `com.apple.Accessibility / AssistiveTouchEnabledByiTunes` over plain lockdown.** This is the old iTunes "Configure Universal Access" path. It needs only a trusted pairing, sits outside the `developer` command tree, and is marked "tunnel-free" in go-ios. go-ios's iOS 17+ end-to-end suite round-trips it ([pymobiledevice3 lockdown_service_provider.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/lockdown_service_provider.py); [go-ios lockdown_assistivetouch.go](https://github.com/danielpaulus/go-ios/blob/main/ios/lockdown_assistivetouch.go); [go-ios e2e settings_test.go](https://github.com/danielpaulus/go-ios/blob/main/test/e2e/settings_test.go)). Both tools run on Windows, provided Apple's usbmux driver is present (iTunes or the Apple Devices app) and the user taps "Trust" once ([pymobiledevice3 README](https://github.com/doronz88/pymobiledevice3/blob/master/README.md)). The open question is semantic. The key's name suggests a "turned on by computer" flag, and the round-trip test reads back the same key. That proves the value was stored, not that the pointer appears on screen, so this is test T5 below.

The same lockdown channel may also cover the button mappings and Dwell Control. pymobiledevice3's own docstring says lockdownd "forwards any key of this domain to libAccessibility, which stores it as an Accessibility preference" ([lockdown_service_provider.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/lockdown_service_provider.py)). If the per-device "Customize Additional Buttons" mappings, or Dwell Control (which Porthole's wizard currently asks the user to turn off), are ordinary preferences, a backup diff could reveal their key names. Porthole could then write them the same way. This is speculative: no public source names those keys, and the mappings may be tied to a pairing-specific identifier.

Porthole can also avoid needing the mappings at all. The project's own S5 spike on iOS 26.6.1 found that **consumer AC Home (0x223) goes to the Home Screen, and ⌘+Space, typing, ⌘+[ and Escape all work with no mapping**. Only App Switcher, Control Center, Notification Center and Screenshot used mapped buttons 3–6 ([PLAN.md, S5 results](../PLAN.md)). Once the pointer is absolute, those four become gestures that Porthole can perform exactly: a glide from the bottom edge that pauses (App Switcher), or a downward swipe from the top-right or top-left corner (Control Center, Notification Center). Full Keyboard Access offers documented, remappable keyboard commands for the same actions, such as Fn-Up for App Switcher, Fn-C and Fn-N, but enabling it is another manual step and it captures Tab and Space ([Apple iPhone User Guide](https://support.apple.com/en-bn/guide/iphone/ipha4375873f/ios)). Note that the iOS 27 USB project reported that AC Home did nothing and switched to a swipe-up ([PR #99](https://github.com/onehumanbeing/esp32-iphone-agent/pull/99)). Gestures are therefore the version-proof fallback.

The other automation routes are dead ends or worse options. No configuration profile or MDM key turns AssistiveTouch on. The supervised-only `AccessibilitySettings` command covers BoldText, Contrast, Motion, Transparency, TextSize, Touch Accommodations, VoiceOver and Zoom, nothing else. The only AssistiveTouch key in Apple's whole schema is in App Lock, which locks the phone to one app ([apple/device-management settings.yaml](https://github.com/apple/device-management/blob/release/mdm/commands/settings.yaml); [com.apple.app.lock.yaml](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.app.lock.yaml)). Supervision would not help anyway, because it always wipes the device ([Jamf Pro docs](https://learn.jamf.com/r/en-US/jamf-pro-documentation-11.16.0/Supervising_Mobile_Devices_with_Apple_Configurator_2-5_or_Later)). Nugget-style partial restores stop at iOS 26.1 ([Nugget README](https://cdn.jsdelivr.net/gh/leminlimez/nugget@main/README.md)). The best fallback that needs no PC is a Shortcuts **Bluetooth "connected" automation running "Set AssistiveTouch: Turn On" immediately**, which iOS 17+ allows without a confirmation prompt ([Matthew Cassinelli](https://matthewcassinelli.com/automations-run-immediately-shortcuts-notifications/)). The user still has to build the automation by hand, and some users report that mice are missing from the trigger's device list ([Apple Discussions 256144633](https://discussions.apple.com/thread/256144633)).

## Five architectures, ranked for a Windows host

The table ranks the options for the user's iOS 26.6.1 phone, with notes on how each changes under iOS 27. "Latency" means the cost per action; none of these paths has a published motion-to-photon measurement.

| Rank | Architecture | Works on 26.6.1? | Latency | One-time user setup | Main risks | Evidence |
|---|---|---|---|---|---|---|
| 1 | **BLE HOGP absolute mouse + lockdown AssistiveTouch enable** (Porthole's current stack, new report map) | Unknown; confirmed on iOS 27 USB and BLE | Native HID reports; 60 ms settle before each press | Tap Trust over USB once; start BLE pairing from the iPhone; forget and re-pair after the report map changes | Absolute may be ignored on 26; the lockdown key may not show the pointer; iOS 26 composite Shift bug | Strong on 27 (#98, #104, PR #99), contradicted on iOS 13/14 |
| 2 | **Current relative BLE mouse + vision closed loop** (baseline) | Yes, ≤ 8 px on static screens | Re-anchor plus burst; worst cases are seconds | Manual AssistiveTouch, Dwell off, buttons 3–6 | Fails over video; tracking-speed drift | Porthole S3/S5 on the user's phone |
| 3 | **WebDriverAgent hybrid** (BLE for hover and keys, WDA for exact taps) | Yes (WDA ≥ 7 on iOS 26) | **0.6–0.9 s per tap, 1.7–2.7 s per drag**; 0.26 s with an unmerged patch | Developer Mode, UI Automation toggle, free-ID re-sign **every 7 days**, DDI mount after each reboot, tunnel | Fragile tunnels, 10–20 s cold starts, cannot touch the home-indicator zone | SideTap on Windows, appium PR #87 |
| 4 | **CoreDevice universal HID** | **No, iOS 27+ only** | Fire-and-forget reports; about 1 s connect per session | Developer Mode, DDI, UI Automation consent | Reports dropped unless a CoreDevice screen stream is running; no ack | go-ios PR #849, pymobiledevice3 |
| 5 | **USB-C microcontroller absolute HID** (ESP32-S3 / RP2040) | Same unknown as #1 | Native USB HID | Plug in a dongle | Extra hardware; a USB-only stuck-pointer bug | esp32-iphone-agent #98, #104 |

Option 1 wins because it keeps everything that already works: no iOS app, no signing, no Developer Mode, the same WinRT GATT server, and the same AirPlay mirror. It changes only the bytes iOS receives. Apple's DTS engineers say a HID accessory is the only supported external input path, and that a computer simulating a Bluetooth HID device is a legitimate way to build one, with no MFi needed ([Apple Developer Forums 794952](https://developer.apple.com/forums/thread/794952)). The BLE-specific risk is a June 2026 report from iOS 26: a composite keyboard + consumer + mouse device, adopted as an AssistiveTouch pointer, has **Shift stripped from typed text**. Splitting the device into two HID services did not help, and Apple has no confirmed workaround (FB24023642) ([Apple Developer Forums 835175](https://developer.apple.com/forums/thread/835175)). Porthole's typing passed S5, but capitals and symbols should be retested once the mouse collection changes.

Option 3 is already partly built. `src/touch/wda.c` has session, tap, drag and pinch calls. Its cost is setup and speed. The default `/wda/tap` takes 918 ms and a drag 2.66 s, because XCTest waits for the event-synthesis daemon to confirm. Zeroing the idle and animation timeouts saves only about 2%. A "fast" route that brings taps to 263 ms remains unmerged after review concerns about stuck queues ([appium/appium-ios PR #87](https://github.com/appium/appium-ios/pull/87)). On Windows, Sideloadly leaves the nested `WebDriverAgentRunner.xctest` unsigned, so SideTap re-signs the whole IPA with go-ios. Free-ID signatures expire every 7 days, and WDA touches "never reach the home-indicator zone" ([SideTap README](https://github.com/ucsandman/SideTap)). WDA works as a precise-tap mode for power users, not as a way to follow the mouse live.

Option 4 is what Porthole wanted, but it is out of reach on iOS 26. `com.apple.coredevice.hid.universalhidservice`, served by `dtuhidd` from the Developer Disk Image, takes normalized absolute touch, up to five-finger multi-touch, keyboard and hardware buttons. It is **not advertised below iOS 27**: an iOS 18.7.3 device returned error 9021. Its reports are thrown away unless a screen stream is running ([go-ios PR #849](https://github.com/danielpaulus/go-ios/pull/849); [pymobiledevice3 CLI recipes](https://doronz88.github.io/pymobiledevice3/latest/guides/cli-recipes/)). pymobiledevice3's `display serve-web` already runs mirroring plus touch from Windows in a browser on iOS 27, so a working reference exists ([screen-mirroring guide](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/screen-mirroring.md)).

Several options are ruled out. Digitizer, touch-screen and pen descriptors produce no response on iPhone. iPhone Mirroring is Mac-only, tied to an Apple Account, and withheld in the EU ([Apple Support 120421](https://support.apple.com/120421)). Phone Link cannot mirror or control an iPhone. Remote-desktop tools are view-only "due to Apple's system restrictions" ([DeskIn FAQ](https://deskin.io/support/faq/cant-control-iphone-ipad)). The EU DMA interoperability decision opens no input channel ([European Commission](https://digital-markets-act.ec.europa.eu/commission-provides-guidance-under-digital-markets-act-facilitate-development-innovative-products-2025-03-19_en)). Voice Control's grid and Switch Control point scanning are coarse, timing-based, and also need manual enabling.

## Recommended path: run one spike, then build in three layers

**On iOS 26.6.1**, start on the Linux/BlueZ backend, because it gives the fastest loop, and port to WinRT once the result is known. **T1, the absolute-descriptor spike**, adds report ID 4: a copy of the esp32 absolute mouse (3 buttons + 5 padding bits, X/Y 16-bit 0..32767 with Physical Min/Max, relative wheel). It also builds a "pure" variant that replaces report 2. Because a bonded iPhone keeps its GATT state ([PLAN.md](../PLAN.md)), forget the device and re-pair after each map change. This is an inference: iOS probably caches the report map. Send position-only reports to a 5×5 grid, then move, wait 60 ms, press and release. Run this in Safari (a pointer-events test page), on the Home Screen and in Settings. Measure the error from the mirrored frame. Pass means all 25 taps land within 1% of screen width with no anchoring. If the pointer does not move, retry with AssistiveTouch toggled off and on, and with the pure variant, before declaring failure. **T2, quirks**: sweep the settle delay (0/20/40/60 ms) to find the lowest that works, check drag gliding against flick behaviour, check that the Home swipe and the App Switcher/Control Center/Notification Center gestures fire from exact edge coordinates, test wheel scrolling, and confirm that landscape orientation still maps 0..32767 to the rotated screen. This last point is untested anywhere. **T3, keyboard regression**: type `Aa!1?` to catch the iOS 26 composite Shift bug with the new map.

Next, automate setup. **T4, lockdown AssistiveTouch**: with AssistiveTouch off and the phone trusted over USB, run `pymobiledevice3 lockdown assistive-touch on` and confirm the pointer appears when Porthole's BLE link connects. Also check whether the Settings switch shows the change, whether the setting survives a reboot, and whether the same write works over Wi-Fi lockdown after `lockdown wifi-connections on` ([tunnels guide](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/ios17-tunnels.md)). If it works, write the minimal lockdown client natively, or ship the go-ios binary, so Porthole stays C. **T5, preference discovery** (optional): back up the phone with `pymobiledevice3 backup2`, change Dwell Control and one button mapping, back up again, diff the accessibility plist, and try writing the changed keys through lockdown on a clean phone. **T6, Shortcuts fallback**: check whether "Porthole" appears in the Bluetooth automation trigger list on 26.6.1. **T7, Windows parity**: publish the new map through the WinRT GATT server and measure end-to-end latency by timestamping a PC mouse event against the frame in which the dot or touch response appears in the UxPlay stream.

The decision gates are simple. If T1 passes, make absolute pointing the default, drop the button-mapping and calibration wizard steps, and keep the vision detector only as a check that the pointer exists. The setup wizard then shrinks to Trust, pair, done. If T1 fails, keep option 2 as the default. Offer WDA (option 3) as an opt-in precise-tap mode with automatic weekly re-signing. Tell the user honestly that updating to iOS 27 unlocks exact control.

**On iOS 27 and later**, run T1–T4 again first. The BLE absolute mouse is already confirmed there, which makes it the default with no Developer Mode required. Then add a power-user backend on option 4. Use pymobiledevice3's `developer core-device universal-hid-service session` or go-ios over an iOS 17.4+ userspace tunnel (no admin, no driver on Windows), mount the Cryptex DDI, keep a CoreDevice display stream open so reports are not discarded, and measure tap latency and true multi-touch (pinch, long-press). This backend needs no AssistiveTouch, and it takes coordinates normalized to 0–65535, so the PC window position maps to it directly. Evaluate whether its screen stream could replace AirPlay entirely, which would remove the double pipeline. The catch: serve-vnc is macOS-only because of HEVC decoding, while serve-web decodes in the browser through WebCodecs, so Porthole would need its own HEVC path on Windows ([pymobiledevice3 PR #2154](https://github.com/doronz88/pymobiledevice3/pull/2154)).

## Conclusion

Positioning was never a computer-vision problem. Porthole sent relative reports to a device whose pointer model became absolute-capable at some point between iOS 14 and iOS 27, and nobody has checked whether that point came before 26.6.1. One afternoon with a modified report map resolves the question. If it passes, Porthole moves ahead of every commercial product that uses the same AirPlay-plus-BLE design. All of them still tell users to set Tracking Speed 6 and hope.

"Fully automatic" has a fixed floor on iPhone. Pairing must start on the phone, trust needs a tap, and every route that skips AssistiveTouch (WDA, CoreDevice) requires Developer Mode. The realistic goal is one-time setup measured in taps rather than settings screens. The lockdown accessibility channel is the least-explored part of that goal: if it accepts arbitrary AssistiveTouch preferences, the setup wizard could disappear entirely.
