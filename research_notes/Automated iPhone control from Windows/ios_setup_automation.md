# Automating or minimizing the iPhone-side setup (AssistiveTouch, pointer button mappings) from a Windows PC

Scope: the ways to turn on AssistiveTouch and related accessibility input modes, and to configure pointer-device button mappings, tracking, dwell and similar settings on iOS 17–26 (user is on iOS 26.6.1) without walking the user through Settings. Each mechanism is listed with what it needs. Research date: 2026-11-18. Notes on method: Apple's MDM schema and the pymobiledevice3 and go-ios source trees were downloaded and read directly (GitHub `release`/`master`/`main` branches as of this date). Apple's schema repo is already at the "27.2" change set, so iOS 27 has shipped. Flagged where behavior is iOS 27-only.

## 1. Can configuration profiles (.mobileconfig) or MDM payloads set accessibility options, including AssistiveTouch? Is supervision required?

### Takeaway
No standard profile or MDM settings key turns on AssistiveTouch, and none configures pointer button mappings, tracking speed or dwell. The MDM `Settings` → `AccessibilitySettings` command (iOS 16+) is supervised-only and covers only BoldText, IncreaseContrast, ReduceMotion, ReduceTransparency, TextSize, TouchAccommodations, VoiceOver and Zoom. The only Apple payload that mentions AssistiveTouch is the supervised-only **App Lock** (Single App Mode) payload. It locks the phone to one app, so it is useless for Porthole.

### Cited Findings
- Apple's MDM `Settings` command has an `AccessibilitySettings` dictionary with `supportedOS.iOS.introduced: '16.0'`, `supervised: true`, and `userenrollment: forbidden`. It is not available on macOS or tvOS. — [apple/device-management mdm/commands/settings.yaml](https://github.com/apple/device-management/blob/release/mdm/commands/settings.yaml)
- The full key list in `AccessibilitySettings` is `BoldTextEnabled`, `IncreaseContrastEnabled`, `ReduceMotionEnabled`, `ReduceTransparencyEnabled`, `TextSize` (0–11, default 4), `TouchAccommodationsEnabled`, `VoiceOverEnabled`, `ZoomEnabled`, and `GrayscaleEnabled` (not available on iOS). There is **no AssistiveTouch, pointer, Switch Control, Voice Control or Full Keyboard Access key**. "The system allows only keys with explicitly provided values." — [settings.yaml](https://github.com/apple/device-management/blob/release/mdm/commands/settings.yaml)
- The `Settings` command applies settings "on a one-time basis. The user may still be able to change the settings at a later time." — [settings.yaml](https://github.com/apple/device-management/blob/release/mdm/commands/settings.yaml)
- ManageEngine (a third-party MDM vendor) documents the same feature as limited to "Supervised Devices running iOS 16.0 or later". — [ManageEngine MDM accessibility settings](https://www.manageengine.com/mobile-device-management/help/profile_management/ios/mdm_accessibility_settings.html)
- The only Apple schema entries containing "AssistiveTouch" are in the **App Lock** profile (`com.apple.app.lock`): `Options.EnableAssistiveTouch` ("If true, the system enables AssistiveTouch") and `UserEnabledOptions.AssistiveTouch` (lets the user toggle it). The payload is iOS 6+, **supervised: true**, and `allowmanualinstall: true`. Other options are `EnableVoiceOver`, `EnableZoom`, `EnableInvertColors`, `EnableSpeakSelection`, `EnableMonoAudio`, and `EnableVoiceControl` (iOS 13+). — [com.apple.app.lock.yaml](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.app.lock.yaml)
- App Lock semantics: "the device locks to the specified app until removal of the profile. The device returns to the app automatically upon wake or restart." — [com.apple.app.lock.yaml](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.app.lock.yaml)
- The new declarative configuration `com.apple.configuration.accessibility.settings` is **iOS 27.0+**, supervised-only, system scope. Its only key is `Vision.AllowLiveRecognition`, so there is no AssistiveTouch or pointer configuration. — [declarative accessibility.settings.yaml](https://github.com/apple/device-management/blob/release/declarative/declarations/configurations/accessibility.settings.yaml)
- The macOS `com.apple.universalaccess` payload exists but is macOS-only, so it does not apply to iPhone. — [Apple Platform Deployment – Accessibility MDM payload](https://support.apple.com/en-gb/guide/mdm/mdme3493u8ap/web)
- A grep of the whole apple/device-management repo (profiles, commands, declarative and skip keys) for "AssistiveTouch" finds only the App Lock entries. No key exists for pointer devices or button customization. — [apple/device-management repo](https://github.com/apple/device-management) (searched locally at release branch, 27.2 change set)

### Inferences
- MDM or profiles cannot do the Porthole-specific steps: turning on AssistiveTouch in normal (non-kiosk) use, and mapping buttons 3–6. Even the keys that exist (Zoom, VoiceOver and so on) need a supervised device plus an MDM server sending commands. That is a heavy ask for a consumer app.
- In principle a supervised device could install an App Lock profile with `EnableAssistiveTouch` and then remove it. Whether AssistiveTouch stays on after the profile is removed is untested. It would also force the device into Single App Mode while the profile is installed. Not viable for normal users.

### Gaps
- No source confirms that AssistiveTouch stays on or reverts when an App Lock profile is removed.
- I found no Apple statement explaining why AssistiveTouch is absent from `AccessibilitySettings`.

## 2. Apple Configurator and Windows alternatives: supervising an iPhone or installing profiles from Windows. Does supervision require erasing the phone?

### Takeaway
Supervision always means erasing the phone (Apple, Jamf). Apple Configurator is Mac-only (or Apple Configurator for iPhone, which only adds devices to ABM/ASM at Setup Assistant). On Windows, open-source tools (pymobiledevice3 `profile supervise`, go-ios `ios prepare`) can write a supervised cloud configuration through the lockdown `mcinstall` service. They can also install profiles: unsupervised installs need the user to approve on the device, and with a supervision identity the install is silent. Since no profile key turns on AssistiveTouch (Section 1), supervision does not help Porthole.

### Cited Findings
- "Any time you supervise or unsupervise a mobile device, the device is wiped." — [Jamf Pro docs: Supervising Mobile Devices with Apple Configurator](https://learn.jamf.com/r/en-US/jamf-pro-documentation-11.16.0/Supervising_Mobile_Devices_with_Apple_Configurator_2-5_or_Later)
- Apple Configurator steps are on Mac: Actions → Prepare → Manual Configuration → "Supervise devices". Changing the supervision identity later requires erasing, preparing and supervising again. — [Apple Configurator User Guide: Prepare manually](https://support.apple.com/guide/apple-configurator-mac/cad99bc2a859/mac)
- Apple Configurator for iPhone (no Mac) requires the target to be at the Wi-Fi pane of Setup Assistant and only enrolls into ABM/ASM. — summarized from MDM-vendor guides in search results ([Hexnode Apple Configurator guide](https://www.hexnode.com/mobile-device-management/help/apple-configurator-mdm-enrollment.md); [Meraki](https://documentation.meraki.com/Platform_Management/SM_-_Endpoint_Management/Install_and_Get_Started/Device_Enrollment/Enrolling_and_Supervising_Apple_Devices_using_the_iOS_Apple_Configurator_app)). These are secondary sources.
- pymobiledevice3 (Windows/Linux/macOS) `profile install`: "Without --keybag the device asks the user to approve each profile; with a supervision identity (supervised devices) it is installed silently." — [pymobiledevice3 cli/profile.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/cli/profile.py)
- pymobiledevice3 `profile supervise ORG [--keybag]`: "Activates the device first if it is not activated yet, then writes a supervised cloud configuration that registers the supervision identity". It also has `profile erase-device` (destructive) and `profile create-keybag`. — [pymobiledevice3 cli/profile.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/cli/profile.py)
- go-ios `ios prepare --certfile --orgname` supervises an activated device by sending `SetCloudConfiguration` with `IsSupervised: true` and `SupervisorHostCertificates`. `ios erase` and `ios profile add [--p12file]` are also available. — [go-ios ios/mcinstall/prepare.go](https://github.com/danielpaulus/go-ios/blob/main/ios/mcinstall/prepare.go); [go-ios main.go usage](https://github.com/danielpaulus/go-ios/blob/main/main.go)
- pymobiledevice3 runs on Windows. It needs iTunes or the Apple Devices app for usbmux, then USB, unlock, and tap "Trust". — [pymobiledevice3 README](https://github.com/doronz88/pymobiledevice3/blob/master/README.md)

### Inferences
- Writing a cloud configuration only works on a device that has not finished Setup Assistant. This matches Apple's "erase required" rule, and go-ios requires the device to be "activated" but not yet set up. So supervision from Windows is technically possible but needs a factory reset. Unacceptable for a consumer mirroring app.
- Installing an unsupervised profile from Windows is easy (user approves in Settings → Profile Downloaded). No accessibility-related profile payload exists for unsupervised devices, so it buys nothing here.

### Gaps
- I did not verify whether iMazing (Windows) can supervise devices or push App Lock profiles. Its Configurator features were not checked.
- Not tested: whether `profile supervise` succeeds on a device that has already been through Setup Assistant on iOS 26 (expected to fail or require erase).

## 3. Shortcuts, Siri, Accessibility Shortcut and Back Tap: toggling AssistiveTouch and triggering it remotely

### Takeaway
Shortcuts has a built-in **Set AssistiveTouch** action (Turn/Toggle, On/Off). Since iOS 17, a **Bluetooth "is connected" personal automation** can run it **immediately** (no confirmation prompt, though a notification is always shown). The user builds that automation once, and AssistiveTouch can then turn on automatically whenever Porthole's BLE HID connects. Other one-time-setup triggers: Siri ("Turn on AssistiveTouch"), the Accessibility Shortcut (triple-click side button), and Control Center. None can be installed onto the phone from the PC. The user must create the automation, though a shared iCloud shortcut link can cut that down to "add shortcut" plus creating the automation.

### Cited Findings
- The "Set AssistiveTouch" action takes Turn/Toggle/Ask Each Time and On/Off. Its "parameters cannot be set using variables". It was added to the action catalog in 2019 (iOS 13 era). — [Matthew Cassinelli – Set AssistiveTouch](https://matthewcassinelli.com/actions/set-assistivetouch/)
- iOS 17: "Bluetooth, Wi-Fi, Arrive, and Leave automations now have the option to run immediately". Apple requires that these always notify; the "Notify When Run" toggle disappears with Run Immediately. — [Matthew Cassinelli – All automations now run immediately](https://matthewcassinelli.com/automations-run-immediately-shortcuts-notifications/)
- The Bluetooth trigger lets you pick a device and choose connected or disconnected. — [xray.tech Apple Shortcuts guide](https://xray.tech/post/apple-shortcuts)
- An Apple Support Communities thread (Sept 22, 2025, iPad) recommends exactly this: a Bluetooth automation on the mouse plus "Set AssistiveTouch" set to Toggle and Run Immediately. Related threads report the **mouse sometimes not listed** in the Bluetooth trigger's device list. — [Apple Discussions thread 256144633](https://discussions.apple.com/thread/256144633)
- Apple: turn on AssistiveTouch via Settings, via Siri ("Turn on AssistiveTouch"), or via Settings → Accessibility → Accessibility Shortcut (triple-click). The Accessibility Shortcut is also reachable from Control Center. — [Apple Support – Use AssistiveTouch (111794)](https://support.apple.com/en-us/111794)
- A June 2026 iDownloadBlog guide covers quickly showing and hiding the AssistiveTouch button (time/location automations with Set AssistiveTouch). — [iDownloadBlog 2026-06-03](https://www.idownloadblog.com/2026/06/03/toggle-ios-assistivetouch-quickly/)

### Inferences
- Best low-friction option without root or supervision: Porthole onboarding tells the user to (a) add a shared "Porthole: AssistiveTouch on" shortcut and (b) create a Bluetooth → "Porthole" → Connected → Run Immediately automation. Whether a BLE HID peripheral appears in the trigger's list is **not confirmed**. The thread above suggests mice sometimes don't, so this needs testing on iOS 26.6.1 with Porthole's GATT HID identity.
- Toggle is risky (connect/disconnect flapping could leave it off). Use "Turn On" on connect and optionally "Turn Off" on disconnect.
- Triggering from the HID keyboard alone: hardware-keyboard text entry works without AssistiveTouch. In theory, Porthole could type a shortcut name into Spotlight or Type-to-Siri, but that needs the user to open Spotlight first. That keyboard shortcut (Cmd-Space) working on iPhone is **unverified**. Treat as speculative.
- Back Tap can be set to AssistiveTouch or a shortcut, but needs physical tapping, so it can't be triggered remotely. (Apple's AssistiveTouch article does not cover Back Tap, and I did not fetch a primary source for it.)

### Gaps
- Not confirmed on iOS 26 that a BLE HID peripheral (as opposed to a classic BT mouse) is listed in the Bluetooth automation trigger.
- No Shortcuts action exists (to my search) for pointer-device button mappings, tracking speed or dwell. Only on/off toggles were found for AssistiveTouch. Not exhaustively verified against the iOS 26 action list.
- Shortcuts automations cannot be created remotely from a PC. Shared shortcuts (iCloud links) can be imported, but automations cannot.

## 4. Are AssistiveTouch per-device button customizations stored per Bluetooth device, do they persist across re-pairing, and can they be set by profile or backup restore?

### Takeaway
The Settings UI is per-device: Settings → Accessibility → Touch → AssistiveTouch → Devices → [device] → Customize Additional Buttons. No source documents the storage format or whether it survives unpair/re-pair. Profiles cannot set it (Section 1). Backup-restore tricks (Nugget's SparseRestore/BookRestore) **do not cover iOS 26.6.1**: SparseRestore covers iOS 17.0–18.1.1, BookRestore covers 18.2–26.1, and Apple patched the partial-restore method in iOS 27. A full backup restore would carry accessibility prefs but replaces the whole device.

### Cited Findings
- iOS 17/26 flow: Settings → Accessibility → Pointer devices / AssistiveTouch → Devices → select device → "Customise Additional Buttons" → press the button → choose action. Defaults: left = Single-Tap, right = Right-Click. — [AbilityNet: Mouse/trackpad with iPhone in iOS 26](https://mcmw.abilitynet.org.uk/how-to-make-it-easier-to-use-a-mouse-or-trackpad-with-your-iphone-or-ipad-in-ios-26)
- The Nugget README says: "Sparserestore works on all versions iOS 17.0-18.1.1." and "BookRestore works on all versions iOS 18.2-26.1." Also: "Mobilegestalt and AI Enabler tweaks are not supported on iOS 26.2+". On iOS 27 it warns against use: "Apple has patched the partial restore method that Nugget uses." It runs on Windows with iTunes or Apple Devices plus pymobiledevice3. — [Nugget README](https://cdn.jsdelivr.net/gh/leminlimez/nugget@main/README.md)
- The underlying restore flaw (crafted backup modifying protected files) was fixed in iOS 18.2 as CVE-2024-54525 (third-party database, unverified). — [SentinelOne CVE-2024-54525](https://www.sentinelone.com/vulnerability-database/cve-2024-54525/)
- **Lockdown back door for accessibility prefs:** pymobiledevice3's docstring for `set_auto_answer_calls` says: "lockdownd forwards any key of this domain [`com.apple.Accessibility`] to libAccessibility, which stores it as an Accessibility preference. Reading it back through lockdownd is not possible, as it only serves the `*EnabledByiTunes` keys." — [pymobiledevice3 lockdown_service_provider.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/lockdown_service_provider.py)

### Inferences
- **Speculative but promising:** if the AssistiveTouch per-device button mapping is a plain libAccessibility preference, lockdown `SetValue` into domain `com.apple.Accessibility` might write it from Windows over a normal trusted pairing, with no supervision, MDM or Developer Mode. This assumes the preference key name and value encoding are known. Discovering them: configure buttons manually once, take a local backup with `pymobiledevice3 backup2 backup` (works on Windows), and inspect `HomeDomain/Library/Preferences/com.apple.Accessibility.plist` (or whichever plist changed). Then try writing the same key via lockdown on a clean device. Untested. It might also be ignored if the value is a complex dict/data blob, or if the mapping is keyed by a per-pairing device identifier that changes on re-pair.
- If mappings are keyed by the peripheral's identity, Porthole should keep a **stable BLE identity (static random address / IRK)** so the mapping survives reinstalling Porthole or reconnecting. Unverified whether iOS keys by address, name, or VID/PID.

### Gaps
- No public source gives the preference key name or format for AssistiveTouch "Customize Additional Buttons", or whether it persists after "Forget This Device" and re-pairing. Needs an on-device experiment (backup diff).
- Not checked whether accessibility prefs are included in encrypted vs. unencrypted backups. Device settings are in iTunes/Finder backups in general, but I did not cite this.

## 5. Can pymobiledevice3 / libimobiledevice / go-ios toggle accessibility settings? Do they work from Windows, over USB/Wi-Fi, on iOS 17+?

### Takeaway
**Yes, for AssistiveTouch on/off, with no Developer Mode needed.** Both pymobiledevice3 (`pymobiledevice3 lockdown assistive-touch on`) and go-ios (`ios assistivetouch enable`) write `com.apple.Accessibility / AssistiveTouchEnabledByiTunes` over plain lockdown. This is the legacy iTunes "Configure Universal Access" path. It needs only a trusted pairing, works on Windows, and go-ios marks it "tunnel-free" and round-trip-tests it in its iOS 17+ e2e suite. The same path covers VoiceOver, Zoom and Invert Colors. The separate DVT accessibility-audit "settings" service (Xcode Accessibility Inspector overrides) needs Developer Mode and covers display/text overrides, not AssistiveTouch (unconfirmed). On **iOS 27+ only**, pymobiledevice3 offers full screen mirroring plus touch control via CoreDevice (Developer Mode + DDI). That removes the need for AssistiveTouch entirely.

### Cited Findings
- pymobiledevice3 `set_assistive_touch(value)` → `set_value(int(value), "com.apple.Accessibility", "AssistiveTouchEnabledByiTunes")`. It has analogous `VoiceOverTouchEnabledByiTunes` and `InvertDisplayEnabledByiTunes` setters/getters and `CallAudioRoutingAutoAnswerEnabledPreference` (write-only). — [pymobiledevice3 lockdown_service_provider.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/lockdown_service_provider.py)
- CLI: `pymobiledevice3 lockdown assistive-touch [on|off]`: "Show or set whether the AssistiveTouch button is shown on screen." It sits under `lockdown`, not `developer`, so no Developer Mode or DDI is needed. — [pymobiledevice3 cli/lockdown.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/cli/lockdown.py)
- go-ios: `ios assistivetouch (enable | disable | toggle | get) [--force]`, plus `ios voiceover …` and `ios zoom …`. The implementation is `ConnectLockdownWithSession` + `SetValueForDomain(assistiveTouchKey, accessibilityDomain, enabled)`. It refuses below iOS 11 unless `--force` is given. The command registry test asserts "assistivetouch stays tunnel-free". — [go-ios ios/lockdown_assistivetouch.go](https://github.com/danielpaulus/go-ios/blob/main/ios/lockdown_assistivetouch.go); [go-ios main.go](https://github.com/danielpaulus/go-ios/blob/main/main.go); [go-ios command_registry_test.go](https://github.com/danielpaulus/go-ios/blob/main/command_registry_test.go)
- go-ios's iOS 17+ e2e suite has `TestAssistivetouchToggle`, which round-trips `assistivetouch` enable/disable and asserts the state changed. A separate `preios17` suite exists. — [go-ios test/e2e/settings_test.go](https://github.com/danielpaulus/go-ios/blob/main/test/e2e/settings_test.go)
- The DVT accessibility-audit service is `com.apple.accessibility.axAuditDaemon.remoteserver` (RSD shim on iOS 17+). `settings()` → `deviceAccessibilitySettings`, `set_setting(name, value)` → `deviceUpdateAccessibilitySetting:withValue:`, and `reset_settings()`. Setting names come from the device and are not hardcoded. — [pymobiledevice3 services/accessibilityaudit.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/accessibilityaudit.py); CLI `developer accessibility settings show|set|reset` — [cli/developer/accessibility/settings.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/cli/developer/accessibility/settings.py)
- "Developer services (everything under `developer`) need Developer Mode (iOS 16+) … iOS 17+: `developer dvt` needs only Developer Mode. `developer core-device` always needs the DDI." `amfi enable-developer-mode` "only works when no passcode is set". Otherwise the user must reveal and enable it in Settings → Privacy & Security, with a reboot. — [pymobiledevice3 docs/guides/cli-recipes.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/cli-recipes.md)
- iOS 17.4+ tunnels work the same on macOS, Windows and Linux without root. iOS 17.0–17.3 on Windows needs `tunneld` as Administrator. Lockdown over Wi-Fi can be enabled with `pymobiledevice3 lockdown wifi-connections on`, and tunnels can use `-t wifi`. — [pymobiledevice3 docs/guides/ios17-tunnels.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/ios17-tunnels.md)
- iOS 27+: `pymobiledevice3 developer core-device display serve-web` mirrors the screen in a browser on Windows with "Touch: click to tap, drag to swipe", hardware buttons, Home, keyboard, audio and clipboard. Its Accessibility panel changes "text size, color filters, reduce motion, increase contrast and similar settings" on the real device. Requirements: "iOS 27 or later. Older versions don't send the stream", plus Developer Mode and a mounted DDI. — [pymobiledevice3 docs/guides/screen-mirroring.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/screen-mirroring.md)

### Inferences
- **Practical recommendation for Porthole (iOS 17–26):** at first-run, with the phone on USB once (to pair/Trust and optionally enable Wi-Fi lockdown), Porthole can call lockdown `SetValue(domain=com.apple.Accessibility, key=AssistiveTouchEnabledByiTunes, value=1)`. It can do this by embedding pymobiledevice3/go-ios or reimplementing the small lockdown + SSL session protocol in C. This removes the "enable AssistiveTouch" step with no Developer Mode, MDM or supervision. Windows needs Apple's usbmux driver (iTunes or Apple Devices app). Later sessions could reuse the pairing record over Wi-Fi if `EnableWifiConnections` was set.
- The key name "EnabledByiTunes" suggests it may behave as an "enabled by computer" flag rather than the main Settings switch. go-ios's iOS 17+ round-trip test shows the read-back changes. The getter reads the same key, so this does not prove the on-screen button appears. Verify on iOS 26.6.1 that the AssistiveTouch pointer actually appears when the BLE mouse connects.
- Because lockdown reportedly forwards *any* `com.apple.Accessibility` key to libAccessibility (Section 4), it may be possible to set other AssistiveTouch prefs this way, such as button mappings, tracking speed, dwell, or "Show menu always" off. Key names must be found empirically. Speculative.
- On iOS 27+, CoreDevice screen mirroring with touch injection is a fundamentally different path: no BLE HID and no AssistiveTouch. But it needs Developer Mode and USB/tunnel DDI mounting, and the user is on iOS 26.

### Gaps
- No primary source lists the AXAudit `deviceAccessibilitySettings` keys on iOS 26. Whether it exposes AssistiveTouch, Full Keyboard Access or Voice Control was not confirmed (likely only the Xcode environment-override set).
- Not confirmed: whether lockdown `SetValue` to `com.apple.Accessibility` works over Wi-Fi lockdown (vs. USB only) on iOS 26, or whether it prompts the user.
- libimobiledevice: `ideviceinfo -q com.apple.Accessibility` exists generically, but I found no libimobiledevice documentation for setting these keys (`idevicesetting`-style). Not verified.

## 6. Alternatives that avoid AssistiveTouch setup: Voice Control, Switch Control, Full Keyboard Access, Control Nearby Devices, iPhone Mirroring, Phone Link

### Takeaway
Full Keyboard Access (FKA) gives keyboard-only control of the whole UI, including App Switcher, Control Center and Notification Center via Fn-key commands. Porthole's existing BLE keyboard could drive it with no mouse button mapping, but FKA itself must still be turned on. iPhone Mirroring is Mac-only (macOS Sequoia+). Microsoft Phone Link does not mirror or control iPhones as of 2026. No first-party Windows equivalent exists. On iOS 27+, the developer CoreDevice stream (Section 5) is the closest "scrcpy-like" option.

### Cited Findings
- Apple (Full Keyboard Access, iPhone): turn on under Settings → Accessibility → Keyboards → Full Keyboard Access. Commands include Tab-H (help/command list), Tab and Shift-Tab to move, Space to activate, **Fn-H Home Screen, Fn-Up Arrow App Switcher, Fn-C Control Center, Fn-N Notification Center**. Commands are user-remappable under Commands. — [Apple iPhone User Guide – Control iPhone with an external keyboard](https://support.apple.com/en-bn/guide/iphone/ipha4375873f/ios); [AbilityNet iOS 26 external keyboard guide](https://mcmw.abilitynet.org.uk/how-to-control-your-device-using-an-external-keyboard-in-ios-26-on-your-iphone-or-ipad)
- App Lock includes `EnableVoiceControl` (iOS 13+), so Voice Control can be forced on only via a supervised Single App Mode profile. — [com.apple.app.lock.yaml](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.app.lock.yaml)
- Phone Link for iPhone: "Image/video sharing and group messaging are not supported" (Microsoft moderator, Feb 2026). Third-party guides confirm no iPhone screen mirroring or app streaming. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5586798/can-i-mirror-my-iphone-screen-to-my-windows-laptop); [TechSpot](https://www.techspot.com/news/106561-microsoft-improves-windows-11-iphone-integration-nowhere-near.html)

### Inferences
- Porthole could map PC shortcuts (e.g. App Switcher, Control Center, Notification Center buttons) to BLE HID keyboard chords **Fn/Globe+Up, Fn+C, Fn+N, Fn+H** instead of mouse buttons 3–6, *if* FKA is on. This drops the per-device button mapping step but swaps in an "enable FKA" step. Whether Globe/Fn commands work on iPhone *without* FKA enabled (as some do on iPad) is unverified. Sending the Apple Globe/Fn key needs the Apple vendor usage (keyboard "Fn" on vendor page 0xFF) in the HID report descriptor. Unverified implementation detail.
- Whether FKA can be enabled via lockdown's `com.apple.Accessibility` forwarding (Section 4) is unknown. Worth testing alongside AssistiveTouch key discovery.
- Switch Control (a keyboard key as a switch) and Voice Control both need manual enabling and are poor substitutes for direct pointer control. No automation path besides supervised App Lock (Voice Control) was found.
- Control Nearby Devices controls another Apple device *from* an iPhone (same Apple ID). iPhone Mirroring is macOS Sequoia+ only. Neither helps a Windows host. (General knowledge; no primary source fetched this session.)

### Gaps
- No primary source fetched for Switch Control "switch from external keyboard" setup or Control Nearby Devices specifics.
- Not verified whether iOS 26 honors Globe-key system shortcuts (Globe+C, Globe+N) from a hardware keyboard on iPhone without FKA. Needs device testing.
- iMazing or other commercial Windows tools for accessibility configuration were not researched.
