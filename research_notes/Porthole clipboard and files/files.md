# PC ↔ iPhone file transfer (iOS 26.x, non-jailbroken)

Scope: owner’s iPhone 14 Pro on iOS 26.6.1, Ubuntu today, Windows as the product target, no jailbreak, personal use. Date of research: 18 November 2026. No source in this pass was run against that exact phone. Apple’s current iPhone User Guide still has an iOS 26 edition; a newer iOS 27 guide also exists, so iOS 27 bugs are not assumed to apply to 26.6.1.

Existing notes under `research_notes/Automated iPhone control from Windows/` were not used as evidence.

## USB: PTP, AFC, house_arrest, installation_proxy, Apple Devices, Wi-Fi sync — Linux vs Windows, and whether DCIM needs a developer image

### Takeaway
A trusted, unlocked iPhone exposes two different USB file surfaces without a Mac and without a developer disk image: a camera/photo import surface (PTP, used by Windows Photos) and the AFC media chroot plus file-sharing app Documents (libimobiledevice / ifuse / pymobiledevice3 / Apple Devices File Sharing). Developer disk images are for debugging and screenshots, not for reading DCIM.

### Cited Findings
- Apple’s Windows photo import path is: install Apple Devices from the Microsoft Store, connect USB, unlock, tap Trust or Allow, then import in the Microsoft Photos app. If iCloud Photos is on, full-resolution originals must be downloaded to the phone before a PC import. AirDrop is documented only as a way to send photos to a Mac, and Image Capture only for a Mac folder import. — [Apple Support, Transfer photos (published 14 Sep 2026)](https://support.apple.com/en-us/120267)
- Microsoft’s import steps are: data-capable USB cable, phone powered on and unlocked (a locked phone is not found), Photos → Import → connected device. On iPhone, Trust or Allow is required. If a photo exists only in iCloud, import it with iCloud for Windows instead. Not every USB cable can transfer files. — [Microsoft Support, Import photos and videos from phone to PC](https://support.microsoft.com/en-us/windows/apps/photos/import-photos-and-videos-from-phone-to-pc)
- Apple Devices File Sharing copies files only to and from an iOS app that supports File Sharing. Windows 10 or later, current Apple Devices, current iOS. Connect USB, open Files, pick an app, Add File to push, or Save to pull. If no app supports sharing, the Files section is absent. — [Apple Support (SG), Use Apple Devices to share files](https://support.apple.com/en-sg/120402)
- The same File Sharing model on a Mac is Finder (macOS Catalina or later): USB, or Wi-Fi if Wi-Fi sync was already set up; drag files onto an app; copies land in On My iPhone in Files. Apple tells Windows users to use Apple Devices instead of Finder. — [Apple Support, Use the Finder to share files (updated 6 Oct 2026)](https://support.apple.com/en-us/119585); older Windows iTunes guide, same app-document limit, USB or Wi-Fi sync — [Apple Support, Use iTunes to share files](https://support.apple.com/en-us/120403)
- Apple’s Windows sync guide: the first sync setup needs a USB or USB-C cable and possibly Trust. After that, sync can be over Wi-Fi on the same network, by turning on the Wi-Fi sync option while cabled. iCloud and cable/Wi-Fi sync are different mechanisms. — [Apple Support (UK), Intro to syncing with Apple Devices](https://support.apple.com/en-gb/guide/devices-windows/mchl923c1147/1.5/windows/10); Wi-Fi chapter — [Sync content over Wi-Fi](https://support.apple.com/guide/devices-windows/sync-content-over-wi-fi-mchl388b22c3/windows)
- `UIFileSharingEnabled` (“Application supports iTunes file sharing”) is the plist flag for sharing files placed in the app’s Documents directory. Default is NO. — [Apple Developer, UIFileSharingEnabled](https://developer.apple.com/documentation/bundleresources/information-property-list/uifilesharingenabled)
- File Provider docs: a File Provider extension is not required for local documents. On iOS, document-browser apps set `UISupportsDocumentBrowser`; other apps set both `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`. Those files then appear in Files and in a document browser and can be opened in place. — [Apple Developer, File Provider](https://developer.apple.com/documentation/fileprovider)
- Archived Apple wording, quoted on Stack Overflow: in iOS 11 and later, if both `LSSupportsOpeningDocumentsInPlace` and `UIFileSharingEnabled` are YES, the local file provider grants access to all documents in the app’s Documents directory; they appear in Files and a document browser. — [Stack Overflow revision citing Apple’s Info.plist reference](https://stackoverflow.com/revisions/4faafa0a-3af6-455d-bd5e-84dc737150ec/view-source)
- ifuse mounts iOS directories over FUSE using libimobiledevice. Default mount is the AFC media partition, described as the `/var/mobile/Media/` chroot (music and pictures). `ifuse --root` is the jailbreak path and needs the AFC2 service, which only older jailbreaks installed. `ifuse --documents <bundle-id>` mounts that app’s documents folder (example: `org.videolan.vlc-ios`). `ifuse --container <bundle-id>` mounts the app sandbox root. `ifuse --list-apps` lists installed file-sharing apps. — [ifuse README, updated 22 Apr 2026](https://github.com/libimobiledevice/ifuse/blob/master/README.md)
- ifuse’s CLI also has `-n, --network` (“connect to network device”), `--documents`, `--container`, and `--list-apps`. Service name strings in source are `com.apple.afc`, `com.apple.afc2`, and `com.apple.mobile.house_arrest`. `--documents` sends `VendDocuments`; `--container` sends `VendContainer`. `--list-apps` uses installation proxy. — [ifuse.c](https://github.com/libimobiledevice/ifuse/blob/master/src/ifuse.c)
- libimobiledevice’s AFC API is the service `com.apple.afc`, documented as filesystem access on the device (directory listing, file info, read/write). — [libimobiledevice afc.h docs, 1.4.0](https://libimobiledevice.org/docs/libimobiledevice/latest/afc_8h.html)
- libimobiledevice’s own tool list separates “access filesystem” and “access documents of file sharing apps” from “take screenshots (requires mounted developer image)” and from `ideviceimagemounter` (“mount disk images”). — [libimobiledevice README](https://github.com/libimobiledevice/libimobiledevice)
- `ideviceimagemounter` mounts a developer disk image. For iOS 17+, the argument is a directory containing a `.dmg`, `BuildManifest.plist`, and a Firmware subdirectory. On iOS 16+, it refuses to mount unless Developer Mode is enabled (`com.apple.security.mac.amfi` / `DeveloperModeStatus`). The image mounter service is `com.apple.mobile.mobile_image_mounter`. — [ideviceimagemounter.c](https://cgit.sukimashita.com/libimobiledevice.git/tree/tools/ideviceimagemounter.c?id=ca85a1829c275635f7b2854887f6490dcb3c5e40); [mobile_image_mounter.h](https://github.com/libimobiledevice/libimobiledevice/blob/master/include/libimobiledevice/mobile_image_mounter.h)
- pymobiledevice3 is pure Python 3, Windows, Linux, and macOS, and implements lockdown services including AFC. Its README lists developer features (screenshots, DDI mounting, and on iOS 17+ a per-command tunnel with no root, including on Windows and Linux) separately from ordinary device access. Docs: https://doronz88.github.io/pymobiledevice3/ — [pymobiledevice3 README](https://github.com/doronz88/pymobiledevice3)
- `HouseArrestService` talks to `com.apple.mobile.house_arrest` (remote shim `com.apple.mobile.house_arrest.shim.remote`). It vends one app container over AFC. `documents_only` selects `VendDocuments` and the `/Documents` subtree; otherwise `VendContainer`. The command plist is `Command` plus `Identifier` (bundle id). — [house_arrest.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/house_arrest.py)
- ArchWiki: GVFS with `gvfs-gphoto2` exposes photos and videos, not music. `gvfs-afc` exposes the app-document filesystem. `ifuse` with no flags mounts the media filesystem; photos are under `mountpoint/DCIM`; music database is under `mountpoint/iTunes_Control`, and that path can copy songs off the device but cannot add songs. `ifuse --documents APPID` mounts one app. — [ArchWiki, iOS (page updated 14 Nov 2026)](https://wiki.archlinux.org/title/IOS)
- libgphoto2 issue on an iPhone16,2 running iOS 26.5: PTP detects the phone, storage is “Internal Storage”, filesystem type “Digital Camera Layout (DCIM)”, access capability reported Read-Write, but folder listing was empty because of a bad PTP parent-object value. The reporter could still browse the same phone in KDE Dolphin over AFC. usbmuxd and PTP are different USB interfaces. — [libgphoto2 issue #1254, 3 Jun 2026](https://github.com/gphoto/libgphoto2/issues/1254)
- A later libgphoto2 report against iOS 27 beta says PTP `GetObjectInfo` mis-names HEIC and Live Photo MOV objects as `.AAE`, so listings abort. That report is a beta of the next major version, not iOS 26.5/26.6. — [libgphoto2 issue #1258, 15 Jun 2026](https://github.com/gphoto/libgphoto2/issues/1258)
- An April 2026 ifuse bug on iOS 15.8 with distro ifuse 1.3.0: pairing validated and `--list-apps` listed file-sharing apps (VLC, Firefox, Documents, Nextcloud, and others), but `--documents` failed with “Failed to start AFC service com.apple.mobile.house_arrest”. GVFS AFC could list containers and not write. This shows version skew, not that house_arrest is gone. — [ifuse issue #118](https://github.com/libimobiledevice/ifuse/issues/118)
- iMazing (Mac and Windows, USB or Wi-Fi, no jailbreak claimed) browses file-sharing app Documents when `UIFileSharingEnabled` is YES, and otherwise says that folder is not accessible. Its file-system view documents `/Media/DCIM` as Camera Roll photos and `/Media/PhotoData` as photo library data. A separate iMazing “Documents” area is dead storage visible only from iMazing, not on the phone. System-level folders are described as read-only. Apps without file sharing are reached through a backup snapshot, not a live sandbox. — [iMazing, browse and transfer](https://imazing.com/guides/how-to-browse-and-transfer-iphone-files-and-folder); [file system view](https://imazing.com/guides/file-system-view-in-imazing); [app files](https://imazing.com/guides/how-to-access-your-iphone-apps-files-and-data)

### Inferences
- Reading DCIM needs a trusted computer and an unlocked phone (and, for iCloud Photos, originals actually stored on the device). It does not need Developer Mode or a mounted developer disk image. Apple’s own import and File Sharing steps never mention Developer Mode, while libimobiledevice attaches that requirement only to screenshots and `ideviceimagemounter`.
- Linux does not need a trusted Mac. usbmuxd plus libimobiledevice/ifuse/pymobiledevice3 speak lockdown directly. Apple ships no Linux equivalent of Finder or Apple Devices; the practical Linux folder UX is ifuse or GVFS.
- Windows “stock” photo copy is PTP-style import through Apple’s driver stack (installed with Apple Devices) into Microsoft Photos. Windows “stock” arbitrary-file copy is Apple Devices File Sharing into an app Documents folder, not a general disk.
- AFC is the richer surface for a Porthole implementation: DCIM originals, and Documents of apps that opted into file sharing, including a personal sideloaded app. PTP is a photo/video import channel and is currently fragile in libgphoto2 on recent iOS even when AFC works.
- `installation_proxy` is the app census (`ifuse --list-apps`, pymobiledevice3 apps). It does not itself transfer files. Installing an IPA still needs a signature and provisioning profile the device will accept; this pass did not re-verify free Apple ID sideload limits on iOS 26.6.1.
- `VendContainer` is implemented, but Apple’s supported computer-facing surface is Documents of file-sharing apps. Treating `VendContainer` as access to every app sandbox would go beyond what Apple and iMazing document for a non-jailbroken phone.
- Wi-Fi lockdown (the same AFC/house_arrest services without the cable) is available only after Wi-Fi sync has been enabled once over USB. On Windows that checkbox is in Apple Devices. ifuse can attach with `--network` once the device is already visible that way. This pass did not confirm a Linux-only command that turns the phone’s Wi-Fi sync flag on.

### Gaps
- No capture from this iPhone 14 Pro on iOS 26.6.1, so AFC write-back into DCIM (drop a file in and have it appear in Photos) is not confirmed. Apple does not document that as an import method.
- Exact pair-record directory on Ubuntu vs Windows was not re-read from current libimobiledevice source in this pass.
- Whether current ifuse/pymobiledevice3 on Ubuntu 2026 can still start `house_arrest` against iOS 26.6.1 was not tested. The iOS 15.8 failure was an old ifuse package.
- 3uTools and iTools were not verified from vendor documentation in this pass.
- Encrypted-backup behavior of `idevicebackup2` / `com.apple.mobilebackup2` (what photo files a backup contains versus a live AFC read) was not opened in source here. The service exists in libimobiledevice’s tool list; it is a different, slower channel than a folder mount.

## Wi-Fi without an App Store app: SMB, WebDAV, a local HTTP receiver, AirDrop, a personal sideloaded app

### Takeaway
The only built-in, no-extra-app, both-directions Wi-Fi path on a stock iPhone is the Files app “Connect to Server” flow, which is an SMB client the user drives by hand. WebDAV is not part of that UI. AirDrop is not a practical third-party receiver on a normal Windows or Ubuntu PC in late 2026. A personal sideloaded app can be the other endpoint, but iOS will not keep a server alive in the background.

### Cited Findings
- Files can access file servers and, separately, cloud-provider apps and external USB/SD storage. Connect to Server: Browse → Connect to Server → local hostname or network address → Guest, or Registered User with name and password → pick the volume. The server then appears under Shared. Disconnect is explicit. Apple’s linked setup for the Mac side is Mac file sharing. — [Apple Support (AU), Connect servers or external devices with Files](https://support.apple.com/en-au/guide/iphone/iph8d8f0f1a0/ios)
- Files can also send files onward from the Files app, and has a page for transferring files from the iPhone to a storage device, a server, or the cloud. — [iPhone User Guide, Files section index](https://support.apple.com/en-au/guide/iphone/welcome/ios) (entries “Send files from the Files app” and “Transfer files from iPhone to a storage device, a server, or the cloud”)
- Third-party writeups of that same screen say the client speaks SMB (`smb://` plus IP or hostname), needs SMB 2 or later, and fails against SMB1-only servers. An Ask Different thread through iOS 18.2 reports a Samba server locked to dialect `SMB3` (meaning 3.1.1) returning `NT_STATUS_NOT_SUPPORTED`, with `server min protocol = SMB3_02` as the working compromise. Guest works only if the server allows it. — [SMBDrop guide, 15 Oct 2026](https://smbdrop.com/guides/files-app-cannot-connect-to-server); [Ask Different](https://apple.stackexchange.com/questions/436703/how-to-solve-ios-files-app-failure-to-connect-to-smb-server-up-to-ios-18); [How-To Geek](https://www.howtogeek.com/devops/how-to-connect-to-network-shares-with-the-ios-files-app/)
- Several 2026 guides state that Files “Connect to Server” has no WebDAV client, so WebDAV needs a third-party app. These are not Apple sentences. — [viovenia, 17 Sep 2026](https://www.viovenia.com/en/blog/set-up-webdav-iphone-ipad); [Everappz](https://everappz.com/docs/howto/how-to-set-up-webdav-server-on-iphone-ipad-for-file-access-and-sharing/); [Stratospherix](https://www.stratospherix.com/articles/how-to-access-filebrowser-locations-from-files-app.php)
- Apple documents AirDrop as sending photos, videos, and documents to a nearby iPhone, iPad, or Mac. The Windows photo article points AirDrop at a Mac, not a PC. — [Apple Support search hits for the iPhone AirDrop guide, Oct 2026](https://support.apple.com/guide/iphone/use-airdrop-to-send-items-to-nearby-devices-iphcd8b9f0af/ios); [Transfer photos](https://support.apple.com/en-us/120267)
- OpenDrop is a Python CLI that is protocol-compatible with AirDrop, but AirDrop runs only over AWDL, so the host must be macOS or Linux running an AWDL stack such as OWL. Contacts-only discovery needs Apple-signed credentials extracted from a Mac keychain; “everyone” was the original non-credential mode. It is experimental, does not authenticate peers, auto-accepts received files, sends one file at a time, and can miss iPhones because receivers often wake AWDL only after a custom BLE advertisement. — [OpenDrop README](https://github.com/seemoo-lab/opendrop/blob/master/README.md)
- As of 5 Nov 2026, proposed Linux kernel AWDL patches plus a user-space `t2-drop` tool target Apple T2 Macs running Linux, not generic PCs. Firmware must advertise `awdl`. — [Phoronix, 5 Nov 2026](https://www.phoronix.com/news/Linux-Kernel-Apple-AirDrop-Code)
- A separate Linux project, omdrop / omdrop-owl, claims AirDrop send and receive only on specific Wi-Fi chips. Documented MediaTek MT7925 can stay associated with an AP on channel 6, 44, or 149. Documented Intel AX200/AX201/AX211 and Intel BE configs drop Wi-Fi while visible. It is not affiliated with Apple. — [NeoTeo, 13 Oct 2026](https://www.neoteo.com/en/airdrop-on-linux-what-omdrop-owl-requires)
- A news summary says that with iOS 26.2 / iPadOS 26.2 / macOS 26.2 or later, a sender outside the receiver’s contacts must enter a code before AirDrop proceeds. This is a secondary report, not an Apple protocol spec. — [Analytics Insight, 17 Aug 2026](https://www.analyticsinsight.net/tech-news/how-to-share-files-between-android-iphone-windows-and-mac-a-complete-guide)
- KDE Connect’s official iOS app (App Store, iOS 14+) states that staying connected in the background is not supported: iOS has no supported way to keep a daemon-style app running, and the app being unresponsive in the background is intended. It also cannot read other apps’ notifications. — [kdeconnect-ios README](https://github.com/KDE/kdeconnect-ios/blob/master/README.md)
- A personal app that sets the two plist keys above shows its Documents folder in Files → On My iPhone, so the user can copy between that folder and an SMB share with no extra server on the phone. — [Apple File Provider](https://developer.apple.com/documentation/fileprovider); [UIFileSharingEnabled](https://developer.apple.com/documentation/bundleresources/information-property-list/uifilesharingenabled)

### Inferences
- For Porthole on Ubuntu or Windows, the no-app Wi-Fi design is a Samba share (SMB 2.1 through SMB 3.0.2, not SMB1, and not “SMB3” meaning 3.1.1 only) plus the user copying in Files. It is manual. It is not drag-and-drop into a Porthole window unless the PC side also watches that folder.
- A local HTTP receiver on the PC does nothing by itself: stock iOS has no “POST the current selection to http://pc:port” gesture. Something on the phone (Shortcuts, a share extension, or a sideloaded app) has to perform the upload, or the phone has to be the server while foregrounded.
- Shipping an AirDrop receiver in Porthole for ordinary Windows and Ubuntu hardware is not realistic in November 2026. AWDL is the blocker, not just a missing URL scheme. Contacts-only mode also wants Apple identity keys from a Mac.
- A personal sideloaded app is viable for the owner because they can trust their own provisioning, but it is a second install path (Xcode on a Mac was already in Porthole’s scope) and it will not run as a background NAS.

### Gaps
- Apple’s Files page text retrieved here says “file server” and Guest/Registered User, but the fetched page did not include the literal word “SMB”. SMB is established by consistent secondary sources and by Samba interoperability reports, not by a sentence copied from Apple in this pass.
- No Apple document found in this pass says “WebDAV is unsupported.” The claim is from third-party guides.
- No test of Files → Samba on this Ubuntu host (dialect, encryption required, guest, write-back of a HEIC and a large video).
- iOS 26.6.1 behavior of the reported 26.2 AirDrop contact code was not checked on Apple’s release notes.
- Local Network privacy prompt wording for a sideloaded app on iOS 26 was not pulled from Apple’s privacy docs.

## What a share sheet, Shortcuts, or a personal app can send and receive on the LAN, and how pairing works

### Takeaway
Any LAN send from the phone is user-initiated and app-mediated. A share extension or Shortcuts can push files the user just picked; a foreground personal app can also receive. USB trust is a different pairing system from LAN app pairing. iOS suspends the app when it leaves the foreground, so a phone-hosted server is not a standing share.

### Cited Findings
- KDE Connect iOS is a real App Store app that uses the LAN, but the project says background daemon behavior is unsupported and notification sync is impossible because an app cannot read other apps’ notifications. — [kdeconnect-ios README](https://github.com/KDE/kdeconnect-ios/blob/master/README.md)
- As of 27 Dec 2025, KDE’s own tracker said sending files from the iOS share sheet was not implemented, and a share extension was only proposed. Large files were expected to need extra background permission. — [KDE Phabricator T18405](https://phabricator.kde.org/T18405)
- LocalSend’s protocol (app required on each device, including a mobile/iOS build): discovery can use UDP multicast `224.0.0.167:53317`; the receiver hosts HTTP on TCP `53317`; upload is `POST` of metadata then file bytes; the receiver accepts, partially accepts, or rejects; optional PIN; HTTPS fingerprint is the SHA-256 of the certificate. One party must be able to run an HTTP server. — [localsend/protocol](https://github.com/localsend/protocol)
- LocalSend GitHub issues: iOS build enforces HTTPS; a Linux receiver on plain or self-signed HTTPS has failed iPhone sends with `ConnectionRefused` to `https://<ip>:53317/api/localsend/v1/info` while Linux→iPhone worked (iOS 18.5, LocalSend 1.17.0). Sharing a large Photos selection (hundreds of images) has failed or dropped files in the share-sheet path. Saving an unsupported type such as WebM into the iOS photo library returns `NOT_SUPPORTED_FORMAT`. — [issue #2653](https://github.com/localsend/localsend/issues/2653); [issue #1268](https://github.com/localsend/localsend/issues/1268); [issue #2687](https://github.com/localsend/localsend/issues/2687)
- A 2026 browser-upload writeup: an `<input type="file">` Photo Library pick on iOS (Safari, Chrome, Firefox, Edge) commonly transcodes HEIC to JPEG before the page sees it, even if `accept` includes `image/heic`. The original HEIC is what arrives via AirDrop to a Mac, Files as a real `.heic`, or Finder. A Live Photo is a still plus a short MOV. — [DEV Community, 10 Nov 2026](https://dev.to/heicnow/handling-heic-uploads-from-iphones-in-2026-what-breaks-and-how-to-fix-it-58a2)
- USB trust is the lockdown pairing step: unlock, tap Trust, then the computer can import photos. Resetting Location & Privacy is a commonly documented way to force the Trust prompt again; that reset step was not copied from an Apple page in this pass. — [Apple, Transfer photos](https://support.apple.com/en-us/120267); [Microsoft import article](https://support.microsoft.com/en-us/windows/apps/photos/import-photos-and-videos-from-phone-to-pc)
- libimobiledevice pairing exchanges certificates and stores a pair record (host id, root certificate, system BUID) used later by lockdown. DeepWiki’s summary matches the public API (`lockdownd_pair`, `lockdownd_validate_pair`, `lockdownd_unpair`). — [DeepWiki, libimobiledevice pairing](https://deepwiki.com/libimobiledevice/libimobiledevice/4.4-file-and-image-tools)
- OWASP’s iOS document notes: share/open-in is user-chosen; the sender keeps its file; open-in-place is still user-mediated through Files, the document picker, or a document browser, and uses a security-scoped URL. — [OWASP MASTG-KNOW-0122](https://mas.owasp.org/MASTG/knowledge/ios/MASVS-PLATFORM/MASTG-KNOW-0122/)

### Inferences
- Porthole’s intended shape (share sheet on the phone, receiver on the PC, files saved on the PC, owner’s phone accepted without an extra prompt) matches LocalSend’s “sender is the HTTP client, PC is the HTTP server” direction better than a phone-hosted server. That avoids the iOS background-server limit and matches the KDE Connect authors’ own complaint that the phone app dies in the background.
- The share extension must request a file representation, not only a public JPEG, or iOS will hand it a transcoded still. Even then, Photos → share sheet → many files is a known unreliable path; batching and background time need to be designed for, not assumed.
- LAN pairing is not USB trust. USB trust unlocks AFC/PTP. A LAN app still needs its own check (shared secret, TOFU certificate, or “only this IP”) if the share should be limited to the owner’s PC. LocalSend’s model is multicast discovery plus an accept/PIN on the receiver.
- “Accept the owner’s phone with no prompt” is a product choice on the PC. iOS will still show its own share-sheet and, for a sideloaded app, the Local Network permission. Those prompts are not removable.
- Shortcuts can sit in the share sheet and talk to a URL, but this pass did not re-read Apple’s Shortcuts action reference, so exact POST/multipart behavior and whether a shortcut can run unattended are not treated as confirmed.

### Gaps
- Apple’s Shortcuts user guide actions (“Get Contents of URL”, share-sheet input types, personal-automation confirmation) were not fetched.
- Whether an iOS 26 share extension can obtain the original HEIC plus the Live Photo MOV, as opposed to a rendered JPEG, was not tested on this phone. The transcoding evidence is about browser file inputs and about LocalSend’s Photos share path failing in bulk.
- No measurement of how long a sideloaded app is allowed to finish a transfer after the user leaves it (background URL session versus a raw listening socket).
- KDE Connect’s share-sheet task was still open when filed in Dec 2025; it may have landed since. Not re-checked in the repo.

## Drag-and-drop and folder UX in real products, and which of them talk to a stock iPhone

### Takeaway
Folder-style access to a stock, non-jailbroken iPhone is USB/Wi-Fi lockdown (Apple Devices, iMazing, ifuse), not a general network filesystem. LocalSend, Snapdrop/PairDrop, and KDE Connect talk to a stock iPhone only by adding an app or a browser tab. They do not mount the phone.

### Cited Findings
- Apple Devices on Windows: drag files onto a file-sharing app, or Add File / Save. Immediate copy, not a full-library sync. No Files section if the phone has no sharing apps. Photo import is a different app (Microsoft Photos). — [Apple Support (SG)](https://support.apple.com/en-sg/120402); [Apple, Transfer photos](https://support.apple.com/en-us/120267)
- Finder on a Mac is the same drag-onto-an-app model, and transferred files show up under On My iPhone in Files. — [Apple Support, Finder file sharing](https://support.apple.com/en-us/119585)
- iMazing, Mac and Windows, USB or Wi-Fi: drag-and-drop into file-sharing apps; quick-transfer wizard filters by which apps accept which types; file-system browser for media paths including `/Media/DCIM`; backup browser for other apps; explicit “no jailbreak” claim on the product page. One guide says the Files app itself cannot be the quick-transfer destination, so a file-manager app such as Documents or VLC is the on-device inbox. Dead-storage “Documents” is visible only through iMazing. — [iMazing file transfer](https://imazing.com/iphone-file-transfer); [browse and transfer](https://imazing.com/guides/how-to-browse-and-transfer-iphone-files-and-folder); [quick transfer](https://imazing.com/guides/how-to-easily-transfer-documents-photos-music-to-iphone-ipad); [interface](https://imazing.com/guides/learn-imazing-interface)
- ifuse is the open-source folder UX on Linux: the mount looks like a directory in the file manager, but only the media chroot or one app container. `fusermount -u` to unmount. Default AFC mount is not the root filesystem. — [ifuse README](https://github.com/libimobiledevice/ifuse/blob/master/README.md); [ArchWiki](https://wiki.archlinux.org/title/IOS)
- Third-party Windows guides also describe File Explorer → Apple iPhone → Internal Storage → DCIM after Trust. That is not the procedure Apple’s own PC article gives (Apple sends you to Microsoft Photos). — [MacObserver](https://www.macobserver.com/tips/how-to/fix-cant-transfer-photos-from-iphone-to-pc/); [Wondershare](https://mobiletrans.wondershare.com/iphone/how-to-find-missing-iphone-dcim-photos-windows.html)
- LocalSend talks to a stock iPhone only if the LocalSend iOS app is installed. It is send-to-device with an accept step, not a remote folder. Same LAN. Protocol as above. — [localsend/protocol](https://github.com/localsend/protocol); comparison writeups — [Oxolan, 23 Jul 2026](https://oxolan.com/blog/snapdrop-vs-localsend-vs-oxolan)
- Snapdrop and its fork PairDrop are websites: both browsers open, WebRTC on the same LAN; PairDrop can also pair with a code and meet off-LAN. Nothing is installed. No persistent folder, no resume. They work on an iPhone only as a Safari (or other browser) tab, with the phone’s download/file-picker limits. — [Oxolan comparison](https://oxolan.com/blog/snapdrop-vs-localsend-vs-oxolan); [usefwd.io, 31 Oct 2026](https://usefwd.io/blog/localsend-vs-blip-vs-kde-connect-vs-pairdrop/)
- KDE Connect talks to a stock iPhone only with the App Store (or TestFlight) app, and only while that app is effectively in the foreground. It is a paired LAN link, not a USB filesystem. Share-sheet send was still a missing feature in the Dec 2025 task. — [kdeconnect-ios README](https://github.com/KDE/kdeconnect-ios); [T18405](https://phabricator.kde.org/T18405)
- iMazing’s sync-without-iTunes guide: drag-and-drop of individual files does not require a full sync; file sharing still depends on the app flag or on a backup; system folders are read-only. — [iMazing, sync without iTunes](https://imazing.com/guides/how-to-sync-and-manage-your-iphone-or-ipad-without-itunes)

### Inferences
- Products that truly “open the iPhone as folders” without an App Store app are the lockdown tools: Apple Devices (narrow), iMazing (wider, commercial, Mac/Windows), ifuse/pymobiledevice3 (Linux and Windows, media plus sharing apps). 3uTools, iTools, and AirDroid were not sourced here; do not assume they match iMazing.
- Snapdrop/PairDrop are the only options in this set that need nothing installed on the iPhone. They are a poor fit for original photos and for an unattended Porthole receiver, because both ends must sit in a browser and iOS may transcode the pick.
- A Porthole folder UX on Windows can honestly copy iMazing’s split: “Camera Roll” (AFC DCIM, read, originals) and “Porthole inbox” (house_arrest Documents of the personal app, read/write). It should not promise the whole filesystem.
- Apple Devices photo sync (a folder of pictures synced as a library) is a different feature from File Sharing. This pass did not re-read Apple’s photo-sync limitations (deletion on device, album type). A secondary writeup says synced photos cannot be deleted in the Photos app and must be removed from the computer. — [iDownloadBlog, 3 Jan 2025](https://www.idownloadblog.com/2025/01/03/how-to-use-apple-devices-app-on-windows-pc/)

### Gaps
- No primary page was fetched for 3uTools, iTools, or AirDroid. Whether current builds still use lockdown/AFC, require a companion app, or phone home was not established.
- iMazing’s Wi-Fi path is claimed by the vendor; the underlying requirement (Apple Wi-Fi sync already enabled) was not confirmed from their docs in this pass.
- Snapdrop’s official repo was not opened; the comparison articles are secondary.

## Original photo or video versus a screenshot; HEIC, Live Photos, and albums

### Takeaway
USB PTP and AFC copy files that are actually on the device, so a camera original stays HEIC (or JPEG) and a Live Photo stays a still plus a movie, but albums are not folders and iCloud “Optimize” can mean the original is not on the phone at all. Share sheets and browser pickers often substitute a JPEG. A screenshot is just another image in the library, not the original asset.

### Cited Findings
- Apple: iCloud Photos stores original full-resolution photos. Devices may keep full originals or device-optimized versions. For a Windows USB import with iCloud Photos on, originals must be downloaded to the phone first. Setting Camera → Formats → Most Compatible makes new captures JPEG and H.264 instead of the default efficient formats. — [Apple, Transfer photos, 14 Sep 2026](https://support.apple.com/en-us/120267)
- Apple’s storage guide: with iCloud Photos, Optimize Storage defaults on. Full-resolution photos and videos are stored in iCloud and, when needed, space-saving copies are stored on the device. Path: Settings → [name] → iCloud → Photos → Sync this iPhone; on iOS 27 or later an extra iPhone Storage step; the guide says on iOS 26 or earlier you choose Optimize on that Photos screen. — [Apple Support (AU), photo and video storage, 1 Oct 2026](https://support.apple.com/en-au/105061)
- Forensic writeup of an optimized library: full files missing under `/private/var/mobile/Media/DCIM/`, with smaller assets under a thumbnails tree instead. `Photos.sqlite` records original file sizes. This is a jailbreak-style full filesystem view, but it matches Apple’s “originals may not be on device” warning. — [The Forensic Scooter, 5 Dec 2022](https://theforensicscooter.com/2022/12/05/do-you-have-a-full-sized-assetor-just-a-thumbnail-did-optimized-iphone-storage-process-occur/)
- iMazing maps Camera Roll photos to `/Media/DCIM` and library metadata to `/Media/PhotoData`. — [iMazing file system view](https://imazing.com/guides/file-system-view-in-imazing)
- ArchWiki: AFC media mount, photos inside `DCIM`. GVFS PTP exposes photos and videos only. — [ArchWiki](https://wiki.archlinux.org/title/IOS)
- libgphoto2 on iOS 26.5 reports the PTP store as a DCIM camera layout. The iOS 27 beta bug report shows the objects inside those folders are HEIC stills, MOV companions, and `.AAE` sidecars, which PTP then mis-labeled. — [issue #1254](https://github.com/gphoto/libgphoto2/issues/1254); [issue #1258](https://github.com/gphoto/libgphoto2/issues/1258)
- A Live Photo is a still plus motion. Apple has a “Take Live Photos” chapter in the iOS user guide. Third-party transfer docs: between phones the pair can stay a Live Photo; to a browser, cloud, or network drive the sender’s app often delivers only the still. A converter’s on-disk pair is `.HEIC` plus `.MOV` sharing an Apple content identifier. — [iPhone User Guide camera index](https://support.apple.com/en-au/guide/iphone/welcome/ios); [Photo Transfer App KB](https://help.phototransferapp.com/article/149-formats-preserved); [MotionPhoto2AppleLivePhoto README](https://raw.githubusercontent.com/Albresky/MotionPhoto2AppleLivePhoto/main/README.md)
- Browser and share paths lose the original: iOS Photo Library picks are commonly transcoded to JPEG; a Live Photo’s MOV is a separate file that still carries metadata if only the still is cleaned. — [DEV Community, 10 Nov 2026](https://dev.to/heicnow/handling-heic-uploads-from-iphones-in-2026-what-breaks-and-how-to-fix-it-58a2)
- LocalSend on iOS can fail the Photos share sheet when many images are selected, and cannot save arbitrary types (WebM) into the photo library. — [localsend #1268](https://github.com/localsend/localsend/issues/1268); [localsend #2687](https://github.com/localsend/localsend/issues/2687)
- Screenshots are a screen capture saved by the system (Photos), with their own settings chapter. They are not a distinct transfer protocol. — [iPhone User Guide, “Take a screenshot”](https://support.apple.com/en-au/guide/iphone/iphc872c0115/ios)
- A secondary Windows guide says Settings → Photos → Transfer to Mac or PC → Keep Originals avoids a conversion to JPEG on the way to the PC. This was not confirmed from an Apple page in this pass. — [MacObserver](https://www.macobserver.com/tips/how-to/fix-cant-transfer-photos-from-iphone-to-pc/)

### Inferences
- “Original” for Porthole means: copy the bytes out of DCIM (AFC) or import via PTP with Keep Originals, after the user has Download and Keep Originals (or has waited for that download). Do not use a share-sheet JPEG or a screenshot of the mirror window as the photo.
- Albums, Recents, and Hidden are database views (`PhotoData` / `Photos.sqlite`), not directories under DCIM. A folder UI that shows only DCIM will look like a flat camera roll (plus Apple’s `100APPLE`-style buckets), not the user’s albums.
- Live Photo fidelity means copying both the still and the paired movie (and not treating `.AAE` as the photo). A single-file share to a PC app will usually drop the motion.
- Edited photos may have the camera original plus an `.AAE` or a rendered export. Which bytes AFC returns for an edited asset on iOS 26.6.1 was not tested.
- ProRAW/JPEG-XL and spatial video were named in Apple’s camera chapter list but their on-disk names were not collected.

### Gaps
- Screenshot container on iOS 26 (PNG vs HEIC) was not established from Apple.
- Apple’s “Keep Originals” transfer toggle was only found in a secondary article, beside Apple’s separate Camera → Formats → Most Compatible switch, which changes future captures rather than the export of existing HEICs.
- No sample listing of `/DCIM` from an iOS 26.6 device (exact sibling files for a Live Photo, burst, screenshot, and an edited image).
- Whether optimized assets appear in AFC as small JPEGs, as missing files, or as placeholders was not tested; the forensic note is from a full-filesystem acquisition in 2022.

## What is impossible without a jailbreak, and what a personal-use tool can do

### Takeaway
Without a jailbreak the phone will not present its root filesystem, other apps’ private containers, or a reliable background file server, and it will not speak AirDrop to a normal PC. A personal tool on a trusted computer can still copy Camera Roll files that are stored locally, exchange documents with a file-sharing app the owner installed, and use Files→SMB or a foreground share extension for Wi-Fi.

### Cited Findings
- ifuse `--root` needs jailbreak and the AFC2 service. The project says AFC was not made to access the root filesystem, and only older jailbreaks even installed AFC2. Default access is the media chroot. — [ifuse README](https://github.com/libimobiledevice/ifuse/blob/master/README.md)
- DeepWiki’s service table, summarizing libimobiledevice, lists `com.apple.afc2` as root filesystem access on a jailbroken device, distinct from `com.apple.afc`. — [DeepWiki, libimobiledevice](https://deepwiki.com/libimobiledevice/libimobiledevice)
- iMazing: an app sandbox is not accessible from a computer unless file sharing is enabled; other app data comes from a backup, and some apps (the guide names Telegram and Signal) omit their data from backups. System folders are read-only. — [iMazing app files](https://imazing.com/guides/how-to-access-your-iphone-apps-files-and-data); [forensics guide](https://imazing.com/guides/use-imazing-for-ios-forensics-and-e-discovery); [sync guide](https://imazing.com/guides/how-to-sync-and-manage-your-iphone-or-ipad-without-itunes)
- File sharing is opt-in per app via `UIFileSharingEnabled` plus, for Files.app visibility, `LSSupportsOpeningDocumentsInPlace`. — [Apple File Provider](https://developer.apple.com/documentation/fileprovider)
- KDE Connect iOS: no supported persistent background process; cannot read other apps’ notifications. — [kdeconnect-ios README](https://github.com/KDE/kdeconnect-ios)
- AirDrop, as Apple ships it, targets nearby Apple devices, and the open implementations need AWDL hardware plus, for contacts-only, Mac-extracted credentials. — [OpenDrop README](https://github.com/seemoo-lab/opendrop/blob/master/README.md); [Apple AirDrop guide](https://support.apple.com/guide/iphone/use-airdrop-to-send-items-to-nearby-devices-iphcd8b9f0af/ios)
- Developer disk images and Developer Mode are an extra gate for debug services, not the gate for AFC. iOS 16+ refuses the image mount when Developer Mode is off. pymobiledevice3’s iOS 17+ developer tunnel is likewise in the developer-services section of its README. — [ideviceimagemounter.c](https://cgit.sukimashita.com/libimobiledevice.git/tree/tools/ideviceimagemounter.c?id=ca85a1829c275635f7b2854887f6490dcb3c5e40); [pymobiledevice3 README](https://github.com/doronz88/pymobiledevice3)
- Trust plus USB is enough for Apple’s photo import and for File Sharing. Originals that iCloud has evicted are not on the cable. — [Apple, Transfer photos](https://support.apple.com/en-us/120267); [Apple storage guide](https://support.apple.com/en-au/105061)

### Inferences
- Possible for Porthole, personal use, no jailbreak:
  - PC → phone and phone → PC for arbitrary files, USB: a sideloaded (or any file-sharing) app’s Documents over house_arrest, mounted with ifuse or driven by pymobiledevice3, same on Linux and Windows. Apple Devices is the Windows GUI for that same surface.
  - Phone → PC for local photos and videos, USB: AFC read of DCIM, or Windows Photos/PTP import. Preserve HEIC and the Live Photo pair by copying files, not by re-encoding.
  - PC → phone for photos that should appear as normal camera-roll items: not solved by “drop into DCIM” in any Apple doc found here. Apple’s supported pushes are File Sharing, or photo sync of a synced album. Confirm before promising drag-into-Photos.
  - Both directions on Wi-Fi, no App Store app: user copies with Files ↔ SMB share on the PC.
  - Both directions on Wi-Fi, with a personal app: share extension or in-app picker uploads to a PC HTTP server; the app’s Documents folder is the inbox the PC can also read over USB. Foreground only if the phone is the server.
  - Same services over Wi-Fi after a one-time USB pairing and Wi-Fi sync enable, on Windows via Apple Devices.
- Not possible on this non-jailbroken phone:
  - Browse or write `/` or another app’s private container live.
  - Depend on `com.apple.afc2`.
  - Read originals that Optimize Storage has removed, until the phone downloads them.
  - Reconstruct albums from DCIM directory names alone.
  - Keep a NAS, WebDAV, or LocalSend-style listener running on the phone while it is locked or the app is suspended.
  - Receive stock AirDrop on a typical Ubuntu or Windows NIC.
  - Skip Trust, skip the passcode unlock, or skip the Local Network prompt for a third-party app.
  - Install the helper app with no Apple signing. A personal sideload still needs the owner’s Apple ID workflow; limits for a free account on iOS 26.6.1 were not re-verified.
- Developer Mode should stay off unless Porthole later needs screenshots, the developer tunnel, or other DDI services. File transfer does not need it.

### Gaps
- Live test matrix still missing: iOS 26.6.1 × Ubuntu ifuse/pymobiledevice3 AFC read of a known HEIC+MOV pair; house_arrest against a sideloaded bundle id; Windows Apple Devices File Sharing of a PDF both ways; Files app against Samba on Ubuntu; behavior when Optimize Storage is on.
- Whether a modern backup (unencrypted vs encrypted) is a usable photo/export fallback when AFC listing is incomplete was not researched from `idevicebackup2` docs.
- Free-developer provisioning lifetime, number of app IDs, and whether SideStore/AltStore still refresh on iOS 26.6.1 were not checked.
- 3uTools, iTools, and AirDroid current behavior: not sourced.
