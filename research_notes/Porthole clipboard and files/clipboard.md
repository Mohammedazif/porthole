# Bidirectional clipboard: PC (Linux and Windows) and iPhone on iOS 26.x

Scope note for the report writer: owner’s phone is an iPhone 14 Pro on iOS 26.6.1, no jailbreak. Today’s host is an Ubuntu VM; the product target is a Windows PC. Personal use only. Facts below were checked on 2026-11-18. Nothing here was tested on that phone in this pass. “Confirmed” means a primary doc or the cited source states it. Where sources disagree, both are kept.

## Can AirPlay, a HID keyboard, or AssistiveTouch read or write the iOS pasteboard, and what does Porthole’s Alt+V path miss?

### Takeaway
AirPlay mirroring, a Bluetooth or USB HID keyboard, and AssistiveTouch do not read or write `UIPasteboard`. Porthole’s existing paste is one-way PC→iPhone typing: Left Alt+V reads the PC clipboard as plain text and emits US QWERTY HID keystrokes into whatever field is focused. It never sets the iPhone pasteboard, never reads the iPhone pasteboard, and drops images and every non-ASCII byte.

### Cited Findings
- Porthole help text says “V paste clipboard”. The hotkey handler ignores the key unless Left Alt is held, then calls `queue_paste`. Right Alt is not accepted. — `src/main.c` help string; `src/polish/runtime.c` (`KMOD_LALT`, `SDL_SCANCODE_V`, `queue_paste`).
- `queue_paste` copies at most 8191 bytes from `SDL_GetClipboardText` into a 8192-byte buffer. If the clipboard text is 8192 bytes or longer, the paste is refused entirely (`n >= len` returns -1). The encoded queue then keeps at most 2048 key events (`PASTE_MAX`). — `src/polish/runtime.c`, `src/control/paste_sdl.c`.
- Encoding is “Clipboard text as US QWERTY key-downs”. Shift is the only modifier. Bytes `>= 0x80` are skipped. Characters `ph_hid_ascii_to_key` cannot map are skipped. That mapper only accepts printable ASCII plus newline, tab, and backspace, “on a US layout”. — `src/control/paste.h`, `src/control/paste.c`, `src/hid/hid_reports.h`.
- The product plan describes the phone keyboard as Bluetooth HID (“the PC shows up as a mouse/keyboard”), and the planned feature as “Paste PC clipboard text into the iPhone (sent as keystrokes)”. — [PLAN.md](/home/spidewol/Documents/ios-windows/PLAN.md) (v0.1 Bluetooth pairing; v0.2 paste checkbox).
- `SDL_GetClipboardText` is a text API. The paste path never calls an image clipboard API, so a copied picture contributes nothing.
- LetsView’s own Windows guide mirrors an iPhone by Control Center → Screen Mirroring (AirPlay) or by its iOS app’s broadcast. Documented extras are recording, screenshots, and a whiteboard, not the pasteboard. — [LetsView Windows FAQ](https://letsview.com/faq/how-to-use-windows-letsview.html).
- A 2021 walkthrough of ApowerMirror and LetsView lists mirroring, recording, capture, and whiteboard. iOS connects as screen mirroring. It does not describe clipboard sync. — [fossbytes, 2021-05-28](https://fossbytes.com/apowermirror-letsview-mirror-iphone-to-pc-using-these-tools/).
- No Apple AirPlay, HID, or AssistiveTouch document retrieved in this pass says those features expose `UIPasteboard`. AssistiveTouch and Back Tap can launch a Shortcut, and a Shortcut can call Get Clipboard (see the companion-app section). That is the Shortcut reading the pasteboard, not AssistiveTouch.

### Inferences
- Because Alt+V injects keystrokes, text lands only in a focused editable field. It does not update the iOS paste menu, so a later tap of Paste in an app still pastes whatever the phone already had. Secure fields, non-text targets (Photos, Files, the SpringBoard), and a dismissed keyboard receive nothing useful.
- The same limit applies whether the HID transport is Bluetooth or USB. A keyboard usage page has no pasteboard channel; the phone sees keys, not a `UIPasteboard` write.
- An AirPlay receiver can screenshot or record the mirrored pixels. That is a picture of the screen, not the image or text object the user copied. A copied photo that is not currently displayed is invisible to the mirror.
- Non-ASCII is worse than “mojibake”: UTF-8 bytes are dropped, so “café” loses the é bytes and emoji disappear. A string that is long but under 8192 bytes is silently cut at 2048 typeable characters.

### Gaps
- No Apple page was found that says, in those words, “AirPlay mirroring does not sync the clipboard” or “HID keyboards cannot call `UIPasteboard`”. The negative claim is the absence of any such API in the docs and product pages reviewed, plus how Porthole’s own HID path behaves.
- Not checked: whether iOS 26 still ignores HID-injected text in some secure fields, or how fast a long 2048-key paste is accepted.

## Universal Clipboard and Continuity: requirements, and does it reach a non-Apple PC?

### Takeaway
Universal Clipboard copies text, images, photos, and videos between nearby Apple devices on the same Apple Account with Bluetooth, Wi-Fi, and Handoff on. It does not reach Windows or Linux. Apple has agreed to build an EU iPhone↔Windows pasteboard share for paired accessories, with engineering targeted for fall 2027. That API does not exist for Porthole in November 2026, and the reports say it is EU-scoped.

### Cited Findings
- Apple: copy text, images, photos, and videos on one Apple device and paste on another. Requirements: devices near each other; same Apple Account; Bluetooth and Wi-Fi on; Handoff on (default). The item “remains there briefly, or until you replace it by copying something else”. Devices listed for the feature are Mac, iPhone, iPad, and Apple Vision Pro. — [Apple Support 102430, published 2026-02-18](https://support.apple.com/en-us/102430); same requirements on [the UK article](https://support.apple.com/en-gb/HT209460).
- Continuity matrix: Universal Clipboard needs iOS 10 or later (iPhone 5 or later) or any iPadOS, macOS Sierra 10.12 or later, or any visionOS. Copying entire files from one Mac to another needs macOS High Sierra 10.13 or later on each Mac. No Windows or Linux row. — [Apple Support 108046, published 2026-03-17](https://support.apple.com/en-us/108046).
- Handoff is the switch Universal Clipboard rides. There is no separate Universal Clipboard toggle in Apple’s setup steps. Current iPhone path in secondary guides is Settings → General → AirPlay & Continuity → Handoff (the pane name since iOS 18). — Apple articles above; path restated by [Octoclip, 2026-07-04](https://octoclip.app/learn/universal-clipboard-not-working/).
- Apple’s setup text does not say both devices must join the same Wi-Fi network. It says Wi-Fi and Bluetooth must be turned on, and the devices must be near each other. — [Apple Support 102430](https://support.apple.com/en-us/102430).
- Secondary guides agree it never reaches Windows or Android. One vendor guide says Apple’s requirement is not “same Wi-Fi network”, and that the item is a short-lived handoff, not a history. — [Octoclip](https://octoclip.app/learn/universal-clipboard-not-working/); [Clypy, 2026-11-10](https://clypy.app/guides/best-cross-platform-clipboard-manager).
- A 2022 Macworld article says the item lasts about two minutes and that the transfer is end-to-end encrypted. Apple’s current support page only says “briefly” and does not state a duration or the encryption design. Treat two minutes and the E2E claim as unverified against current Apple docs. — [Macworld, 2022-08-20](https://www.macworld.com/article/834342/how-to-control-universal-clipboard.html).
- Developers can keep an item off Universal Clipboard with `UIPasteboard.localOnly`, and can set `expirationDate`. — [OWASP MASTG-KNOW-0083, updated 2026-11-04](https://mas.owasp.org/MASTG-KNOW-0083), citing Apple’s pasteboard API.
- Microsoft asked Apple, under the EU DMA interoperability process (request FB22329535, filed March 2026), for iPhone↔Windows copy/paste. On 26 June 2026 Apple said it would build it. Quoted plan: an extension, patterned on the Accessory Notifications / Accessory Live Activities frameworks from iOS 26.5, is notified when items are copied; it uses the Accessory Transport Extension framework to share them with a paired accessory. The user must consent once per accessory via AccessorySetupKit. Apple called it a significant engineering effort to be finished by fall 2027, then a developer beta, then a public release. Apple did not, in the quoted text, name an iOS version. — [9to5Mac, 2026-08-03](https://9to5mac.com/2026/08/03/apple-plans-to-open-iphone-clipboard-access-to-windows-pcs/); [MacRumors, 2026-08-03](https://www.macrumors.com/2026/08/03/apple-iphone-windows-copy-paste/); [The Verge, 2026-08-04](https://www.theverge.com/tech/975020/apple-windows-pc-copy-paste-eu).
- Headlines that say “iOS 28” or “early 2028 public release” are the outlets’ schedule guess, not a sentence attributed to Apple. Several outlets also say the filing is EU-only. — same three articles; [gHacks, 2026-08-10](https://www.ghacks.net/2026/08/10/apple-confirms-iphone-to-windows-clipboard-sync-after-microsofts-eu-interoperability-request/).

### Inferences
- A Windows PC or a Linux VM cannot join Universal Clipboard by signing into iCloud, turning on Bluetooth, or pairing as a HID keyboard. There is no Apple receiver for it outside Apple’s OSes.
- The fall 2027 EU accessory API is not an implementation option for a November 2026 build. It also does not, on the published description, cover Linux, and it needs a paired-accessory extension plus one-time consent rather than a silent LAN sync.
- If the owner also has a Mac on the same Apple Account, Universal Clipboard already covers Mac↔iPhone, including images and videos. That does not help the Windows/Linux target except as a manual hop.

### Gaps
- Apple’s interoperability portal page was not opened. The June 26 wording is taken from press quotes of that page, which agree with each other, but the portal URL itself was not verified here.
- No current Apple document states the exact lifetime in seconds, a byte cap, or whether a VPN blocks it. Secondary troubleshooting guides mention VPNs and a ~10 m / 30 ft range; those figures are not in the Apple paragraphs quoted above.
- Whether the 2027 feature will ship outside the EU is not stated by Apple in the quotes.

## USB paths that read or write UIPasteboard (pymobiledevice3, lockdown, AFC, DVT, CoreDevice)

### Takeaway
Lockdown file services do not expose the pasteboard. AFC, `house_arrest`, and `installation_proxy` move files and apps, not `UIPasteboard`. The real USB read/write path is CoreDevice `com.apple.coredevice.pasteboardservice`, implemented by a daemon on the mounted Developer Disk Image, over the iOS 17+ RSD tunnel. It needs Developer Mode and a new enough DDI. pymobiledevice3 can SET and PULL text and images on Windows, Linux, and macOS. The documented screen-mirror clipboard UI is iOS 27+ only, because that stream does not start on older systems. A separate report says text copy/paste already worked on iOS 26.2 once a 27A DDI was mounted. iOS 26.6.1 was not tested.

### Cited Findings
- pymobiledevice3 runs on Windows, Linux, and macOS. Its home page (2026-11-17) lists “screen mirroring and control … audio and a shared clipboard (iOS 27+)” and “developer services without Xcode … on iOS 17+ over a no-root tunnel … on Windows and Linux too”. — [docs home](https://doronz88.github.io/pymobiledevice3/latest/); [README](https://github.com/doronz88/pymobiledevice3).
- Developer CLI help: most developer commands need Developer Mode and a mounted DDI (`pymobiledevice3 mounter auto-mount`). `dvt` needs the DDI only on iOS &lt; 17; `core-device` always needs it. On iOS 17+ the services are reached through an RSD tunnel that the tool sets up with no extra flag and no root. — [developer CLI](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/cli/developer/__init__.py).
- Connection rule in the Python guide: classic lockdown (AFC, install, syslog, diagnostics, backup, profiles) works over USB on every iOS version with no root. Developer/DVT on iOS 17+ needs an RSD tunnel (`PreferredRsdTunnel`, no sudo). DVT also needs Developer Mode on iOS 16+, and a mounted DDI on iOS &lt; 17. — [python-api.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/python-api.md).
- The service table in that guide maps `InstallationProxyService` to app install, `AfcService` to media and app-container files, and `MobileImageMounterService` to mounting the DDI. None of those classes is described as a pasteboard client. `house_arrest` is grouped under “Apps, files & profiles”, not pasteboard. — same guide; [API index](https://github.com/doronz88/pymobiledevice3/blob/master/docs/api/index.md).
- `PasteboardService` talks to `com.apple.coredevice.pasteboardservice` (feature `com.apple.coredevice.feature.pasteboard`) with XPC commands `PULL`, `SET`, `DATA`, `PUSH`, `AUTONOTIFY`, `RESOLVE`. `SET` writes text or an image. `PULL` reads a snapshot of items keyed by UTI. Text UTIs tried, in order: `public.utf8-plain-text`, `public.plain-text`, `public.text`. Image UTIs preferred, lossless first: `public.png`, `public.jpeg`, `public.heic`, `public.tiff`, `com.compuserve.gif`, `org.webmproject.webp`, then a `com.apple.webarchive` subresource. The module comment says the wire format was reversed from Apple’s `CoreDevice` / `CoreDeviceUtilities` frameworks, and names the on-device daemon `dtpasteboardd`. — [pasteboard_service.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/remote/core_device/pasteboard_service.py) (master as fetched 2026-11-18).
- Change detection does not poll and does not use `AUTONOTIFY` anymore. `PasteboardMonitor` watches the Darwin notification `com.apple.pasteboard.notify.changed` and then does a `promiseSecondary` PULL (primary type only). `AUTONOTIFY` makes the daemon load every representation before it notifies. Notes advertises `public.rtf`, which fails only after about 64 seconds, and that stall blocks the daemon for every client. Apple’s own `devicectl device pasteboard monitor` is cited as showing the same 64-second delay. A picture that exists only inside a Notes web archive is skipped unless the caller sets `allow_full_pull=True`. `set_text` / `set_image` write the other direction. What was already on the pasteboard when monitoring starts is not reported as a change. — same source; [v11.15.2 notes](https://github.com/doronz88/pymobiledevice3/releases/tag/v11.15.2); [PR 1961, merged 2026-09-17](https://github.com/doronz88/pymobiledevice3/pull/1961).
- v11.15.0 (released 17 September 2026) added two-way clipboard to `serve-web` and `serve-vnc`. `serve-web`: Clipboard → Sync moves text and images; a device JPEG is handed to the browser as PNG; a Notes picture can be recovered from its web archive. The host clipboard is sent when the page regains focus and just before a forwarded Cmd/Ctrl+V. Needs a secure context (`localhost` or `--https`) and the browser clipboard permission. Content already on the device when Sync is turned on is not reported. `serve-vnc --share-clipboard` is text only, via RFB cut-text, UTF-8 if the client supports the Extended Clipboard pseudo-encoding (TigerVNC, noVNC), otherwise Latin-1. — [v11.15.0](https://github.com/doronz88/pymobiledevice3/releases/tag/v11.15.0).
- Current screen-mirroring guide: both viewers need **iOS 27 or later** (“Older versions don’t send the stream, so both commands refuse to start”), Developer Mode, and a mounted DDI. `serve-web` is the cross-platform viewer (browser, WebCodecs). `serve-vnc` is macOS-host only (VideoToolbox). Clipboard behavior matches the release notes, with one later correction: pictures copied out of a rich-text app such as Notes are not shared; copy them from Photos instead. iOS will not start mirroring while a foreground app is using the camera or microphone. — [screen-mirroring.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/screen-mirroring.md).
- A later release note says services such as `com.apple.coredevice.screencaptureservice` and `com.apple.coredevice.hid.universalhidservice` are not part of the iOS base system. Daemons inside the mounted Developer Disk Image provide them, and an older image does not have them. — [pymobiledevice3 releases filtered for iOS 26, v11.53.0 notes](https://github.com/doronz88/pymobiledevice3/releases?q=iOS+26&expanded=true).
- Issue #1744 (opened 2026-06-24, closed 2026-07-01): `developer core-device copy` / `paste` failed on an iPhone 13 (iPhone14,5) running iOS 26.2 and on an iPhone SE running iOS 17.5.1 because `com.apple.coredevice.pasteboardservice` was absent from the RSD service list. Developer Mode was on. An old Personalized DDI (ProductBuildVersion 17A324) was mounted; other CoreDevice services worked. After unmounting it and mounting DDI 27A5194q, the pasteboard service appeared (CoreDevice services went from 7 to 17) and “copy/paste round-trip works perfectly — including Chinese text and emoji”. The reporter’s conclusion: the service requires a matching (new enough) DDI. The maintainer’s first reply was to use `mounter auto-mount`. Host in that report was macOS, not Windows or Linux. Images were not mentioned. — [issue 1744](https://github.com/doronz88/pymobiledevice3/issues/1744).
- Before that remount, the iOS 26.2 RSD list in the bug included `appservice`, `debugserverproxy`, `deviceinfo`, `diagnosticsservice`, `fileservice.control`, `fileservice.data`, and `openstdiosocket`, and no pasteboard entry. So a CoreDevice file service can be present while the pasteboard service is not. — same issue.
- Apple’s Developer Mode article: turn it on under Settings → Privacy & Security so Xcode can run a locally installed app. The switch warns that it reduces security. The user must tap Restart, then after boot confirm (Enable) and enter the passcode. Turning it off also requires a restart. The article does not describe a pasteboard entitlement. — [Enabling Developer Mode, Apple Developer Documentation; search listing updated 2026-11-16](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device).
- Secondary guides say the Developer Mode switch exists on iOS 16 and later and stays hidden until the phone has paired with developer tooling or has a development-signed app installed. A development-signed app (Xcode, AltStore, Sideloadly, a free Apple ID signature) will not launch on iOS 16+ until Developer Mode is on. App Store and TestFlight apps do not need it. — [builds.io, updated 2026-10-20](https://builds.io/blog/ios/developer-mode-ios/); [scarletios, 2026-02-28](https://scarletios.com/how-to-use-scarlet-ios-developer-mode/). These are not Apple pages.

### Inferences
- For this iPhone on 26.6.1, `serve-web` clipboard sync is documented as unavailable: the viewer refuses to start before iOS 27. The lower-level `PasteboardService` might still work if `auto-mount` selects a DDI that advertises `pasteboardservice`. The only positive evidence is one macOS user’s iOS 26.2 phone after a 27A image was mounted. That is not proof for 26.6.1, and not proof on Windows or a Linux VM.
- AFC / DCIM copy is a file transfer of camera-roll items, not a clipboard sync. It can move a photo the user has already saved. It cannot see an image that exists only on the pasteboard, and it cannot place text onto `UIPasteboard`.
- `devicectl` is Apple’s Mac tool hitting the same daemon. It is not a Windows or Linux binary. pymobiledevice3 is the portable client.
- Setup this path actually needs, if the service is present: USB pairing (“Trust This Computer”), Developer Mode with a reboot and passcode, a current DDI mounted, and the iOS 17+ tunnel. The userspace tunnel is documented as no-root on Windows and Linux. A Linux VM only sees the phone if the USB device is passed through to the guest. That last point is an environment constraint, not something the pymobiledevice3 docs spell out.
- Rich fidelity is intentionally lossy. The monitor shares one text string and/or one image. It does not sync a full item list, RTF, or files. Forcing a full pull to recover a Notes image can freeze pasteboard service for about a minute.

### Gaps
- No source states that iOS 26.6.1’s matching DDI includes `dtpasteboardd`. The 26.2 success used an image whose build number starts with 27A. Whether `mounter auto-mount` on 26.6.1 in November 2026 downloads an image that contains the service was not established.
- No Windows or Linux success report for `core-device paste` / `copy` was found. The library is cross-platform; the detailed bug report was on macOS.
- No byte-size ceiling for `SET`/`PULL` was found in the source comments or docs.
- Video UTIs are not in `IMAGE_UTIS`. Whether a copied video survives this service is untested here.
- The CLI’s exact flags (`developer core-device copy` / `paste` versus calling `PasteboardService` from Python) were confirmed by issue #1744 for the commands added in PR 1729. This pass did not re-read the current CLI help to see if those command names changed after September 2026.

## Companion apps, Shortcuts, the share sheet, and local HTTP: what iOS lets an installed app do with the pasteboard

### Takeaway
An app the owner installs may write the general pasteboard, and may read it only in the foreground, with an iOS 16+ paste prompt unless the user uses the system Paste command, `UIPasteControl`, or sets that app’s “Paste from Other Apps” to Allow. Pattern checks do not return the contents and do not prompt. Nothing reviewed can subscribe to “user copied something” while the companion is suspended. Shortcuts can Get Clipboard and Copy to Clipboard when the user runs them, not from a copy trigger, and cannot paste into another app by themselves. A share-sheet or local-HTTP hop is user-started and can carry text and images the user explicitly hands over.

### Cited Findings
- `UIPasteboard.general` is the system-wide pasteboard. Named pasteboards created with `init(name:create:)` are for the same app or the same Team ID, not a bridge to every app. Apple’s overview says writes normally happen because the user asked for copy, cut, or duplicate. — [UIPasteboard](https://developer.apple.com/documentation/uikit/uipasteboard); [OWASP, 2026-11-04](https://mas.owasp.org/MASTG-KNOW-0083).
- Since iOS 14, the system notifies the user when an app gets general-pasteboard content that came from another app without user intent. User intent includes tapping a system control or pressing Command-V. `numberOfItems`, `itemSet(withPasteboardTypes:)`, and the pattern-detection methods are documented as ways to avoid that notification because they do not reveal contents. — [UIPasteboard discussion, Apple docs markdown dated 2026-11-10](https://developer.apple.com/documentation/uikit/uipasteboard.md).
- `detectPatterns(for:inItemSet:)` “only gives an indication of whether a pasteboard item matches a particular pattern and doesn’t allow the app to access the contents”, so the system does not notify. — [detectPatterns](https://developer.apple.com/documentation/uikit/uipasteboard/detectpatterns(for:initemset:completionhandler:)-7ubl1). The older `detectValues` API is documented as reading contents when a pattern matches. — [detectValues listing](https://developer.apple.com/documentation/uikit/uipasteboard/detectpatterns(for:completionhandler:)-5zlnd).
- iOS 16+: programmatic pasting (`UIPasteboard.general.string` and the same class of direct access) raises a user alert before the app receives contents. `UIPasteControl` is a button the person taps; that tap pastes without the alert. Apple DTS: the prompt appears when the app accesses the pasteboard directly, not when it goes through the Paste menu, the keyboard shortcut, or `UIPasteControl`. There is no Info.plist key to request this. The prompt is not granted ahead of time by a usage-description string. — [UIPasteControl, docs updated 2026-10-22](https://developer.apple.com/documentation/uikit/uipastecontrol); [DTS reply, developer forums thread 713770, September 2022](https://developer.apple.com/forums/thread/713770).
- The prompt text reported by app developers is “[App] would like to paste from [Source]”, with Don’t Allow and Allow Paste. — [Tolinku, 2026-06-02](https://tolinku.com/blog/ios-paste-permission-deferred-links/).
- Per-app setting, described consistently by a clipboard-manager vendor and by how-to articles: Settings → Apps → [App] → Paste from Other Apps → Ask, Allow, or Deny. Allow stops the prompt for that app. Deny blocks reading other apps’ copies. There is no API to query that state. A denied read is indistinguishable from an empty pasteboard. — [Paste help](https://pasteapp.io/help/allow-paste-permissions-in-ios); [Stack Overflow, 2025-12-13](https://stackoverflow.com/questions/79846681/how-to-check-paste-from-other-apps-pasteboard-permission-status). The Settings path was not confirmed on an Apple support page in this pass.
- OWASP’s history, which matches Apple’s docs where they overlap: since iOS 9, general-pasteboard reads are limited to foreground apps; since iOS 10, named pasteboards are non-persistent by default and Universal Clipboard is on when the user is signed into iCloud; since iOS 14, a notification on unsolicited reads; since iOS 16, a confirmation dialog. `localOnly` and `expirationDate` exist. — [MASTG-KNOW-0083](https://mas.owasp.org/MASTG-KNOW-0083).
- Shortcuts action `is.workflow.actions.getclipboard` (“Get Clipboard”) “passes the contents of the clipboard to the next action”. Its definition requires `WFMainThreadResource` and lists `UnsupportedEnvironments: ["Background"]`. Output type is generic `WFContentItem` (so it is not text-only at the action-definition level). — [ScPL action dump](https://docs.scpl.dev/actions/getclipboard).
- 2026 how-to articles: a shortcut of Get Clipboard plus Quick Look previews text, images, and files, and iOS may ask whether Shortcuts may paste; the user taps Allow Paste. Copy to Clipboard is described with Expire At and Local Only, matching the developer API. Back Tap, a Home Screen widget, Control Center, or the Action button can run the shortcut. None of the automation triggers fires when the user copies, so the shortcut does not run by itself on copy. — [solveyourtech](https://www.solveyourtech.com/how-to-access-your-clipboard-on-iphone-a-step-by-step-guide/); [Clypy iPhone clipboard guide, 2026-11-10](https://clypy.app/guides/best-clipboard-manager-for-iphone).
- The Paste app’s help says that after Paste from Other Apps is set to Allow, both the app and its keyboard extension read the clipboard without a prompt each time. That is a vendor describing its own app, not an Apple API guarantee. — [pasteapp.io](https://pasteapp.io/help/allow-paste-permissions-in-ios).
- A personal development-signed app needs Developer Mode on iOS 16+ and a one-time Trust of that developer certificate under VPN & Device Management. App Store apps do not. — [scarletios](https://scarletios.com/how-to-use-scarlet-ios-developer-mode/); [Apple Developer Mode article](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device).

### Inferences
- PC→iPhone via a companion: the phone app, while foregrounded, can `setItems` text and images onto `UIPasteboard.general`. The documented prompt is a paste (read) prompt, not a copy prompt. A write from the companion should not raise “would like to paste”. The user still has to Paste inside the destination app, unless the companion is itself the focused editor. This is the opposite of Alt+V, which types immediately and does not fill the pasteboard.
- iPhone→PC via a companion: a reliable read requires a foreground moment and either a prompt, `UIPasteControl`, or Allow. A local HTTP or Bonjour server inside that app can POST the item to the PC only while the app is actually running. iOS will suspend it. There is no documented background mode for “clipboard changed”.
- A custom keyboard is the closest thing to “available while the user is in other apps”, and at least one commercial keyboard does read the pasteboard once Allow is set. That still depends on the user enabling the keyboard and Full Access-style permissions. This pass did not open Apple’s keyboard-extension pasteboard rules, so treat the Paste app page as existence proof for that product, not as the API contract.
- Shortcuts are a zero-install (Apple-signed) version of the same idea. User runs the shortcut, Get Clipboard may prompt once, then “Get Contents of URL” or a share step can send the item to a PC on the LAN. The other direction is: PC serves text, shortcut fetches it, Copy to Clipboard, user pastes. Shortcuts will not inject the paste into Notes by themselves.
- The share sheet is the clean image path that avoids the paste prompt: the user shares the photo, file, or selection to the shortcut or the companion. The system passes that item. It is not a background clipboard mirror.
- Free-account re-sign expiry (often cited as 7 days) and the paid-account one-year window were not re-verified against an Apple document here. Do not bake a number into the plan until that page is opened. Developer Mode and Trust are the parts Apple’s docs do spell out.

### Gaps
- No Apple page retrieved states a maximum pasteboard size for strings or images.
- Not confirmed on iOS 26.6: whether `hasStrings` / `detectPatterns` still avoid the prompt, and whether a widget can read the pasteboard. OWASP still describes widgets as a historical foreground exception; that sentence is not tied to iOS 26.
- Local-network permission strings (`NSLocalNetworkUsageDescription`, `NSBonjourServices`) were not re-read from Apple’s current archive. A LAN companion will need whatever iOS 26 still requires for local TCP and Bonjour; the exact keys should be copied from the current doc before implementation.
- No source confirmed that a personal sideloaded app may use `UIPasteControl` without extra entitlements. It is a public UIKit class.

## Images and rich clipboard versus plain text, and what commercial Windows tools actually sync

### Takeaway
The iOS pasteboard and Universal Clipboard can hold images and, on Apple’s description, videos, not just text. Porthole’s HID paste cannot. The CoreDevice client can move one text value and one inline image (PNG, JPEG, HEIC, TIFF, GIF, WebP), and it gives up on some rich Notes copies rather than block the daemon. No byte cap was found. LetsView and ApowerMirror, used as Windows AirPlay receivers, document screen pixels, recording, and screenshots, not the pasteboard. iMazing, 3uTools, and the Apple Devices app document file, photo, and backup transfer, not clipboard sync. No reviewed Windows product is a confirmed bidirectional iOS pasteboard bridge.

### Cited Findings
- Universal Clipboard’s supported payload, per Apple: text, images, photos, and videos; entire files only between Macs on High Sierra or later. — [Apple Support 102430](https://support.apple.com/en-us/102430); [Apple Support 108046](https://support.apple.com/en-us/108046).
- pymobiledevice3 `PasteboardContent` keeps optional text plus at most one image. A plain-text stand-in that is only whitespace or U+FFFC is dropped when an image is present. `set_image` defaults to `public.png`. Browser sync converts a device JPEG into a PNG the browser clipboard accepts. VNC sync is text, Latin-1 unless the client speaks Extended Clipboard UTF-8. Notes rich copies: primary-type read is immediate; reading every representation can take ~64 seconds and is off by default, so a picture that lives only in the web archive is not shared. — [pasteboard_service.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/remote/core_device/pasteboard_service.py); [screen-mirroring.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/screen-mirroring.md); [v11.15.2](https://github.com/doronz88/pymobiledevice3/releases/tag/v11.15.2).
- Porthole Alt+V: `SDL_GetClipboardText` only, ASCII US QWERTY, 8191-byte hard fail, 2048 key cap. Images never leave the PC clipboard. — `src/control/paste_sdl.c`, `src/control/paste.c`, `src/polish/runtime.c`.
- iMazing’s tools page (updated 2026-07-11) lists Quick Transfer into specific apps, backup, app management, and data export. The feature page lists drag-and-drop files, photos, music, and message export. Clipboard is not in those lists. It runs on Windows and Mac. — [iMazing tools](https://imazing.com/guides/device-tools-in-imazing); [iMazing features, page crawled 2026-11-16](https://imazing.com/app).
- 3uTools is described in 2026 comparisons as a free Windows file, photo, and firmware tool, not as a clipboard or screen-control tool. One guide shows DCIM, Downloads, voice memos, and Books over USB. That is file copy, and HEIC/HEVC still need Windows codecs afterwards. — [DRAKO comparison, 2026-03-18](https://drakoctrl.com/en/blog/iphone-control-software-comparison/); [free-codecs 3uTools guide, 2025-11-01](https://www.free-codecs.com/guides/how-to-access-iphone-file-system-on-pc-with-3utools.htm).
- LetsView: iOS 9 or later, same Wi-Fi, Control Center Screen Mirroring or the LetsView broadcast. Documented features in current reviews are mirroring, whiteboard, and recording. — [LetsView FAQ](https://letsview.com/faq/how-to-use-windows-letsview.html); [Busynessprofile review, checked 2026-11-15](https://busynessprofile.com/best/products/letsview/).
- ApowerMirror: iOS mirroring over Wi-Fi (AirPlay) or USB, plus recording and screenshots. Comparison pages do not list an iOS clipboard. Android remote control is a separate claim from iOS mirroring. — [fossbytes, 2021](https://fossbytes.com/apowermirror-letsview-mirror-iphone-to-pc-using-these-tools/); [TechYorker comparison, 2026](https://techyorker.com/compare/letsview-vs-apowermirror/).
- An existing Porthole note, citing a competitor’s review, says MirrorGo’s shared clipboard and file transfer do not work with iPhone and that keyboard control is not offered for iOS. The note already flags the source as a competitor. — [existing_products_and_constraints.md](/home/spidewol/Documents/ios-windows/research_notes/Automated%20iPhone%20control%20from%20Windows/existing_products_and_constraints.md).
- AirDroid appears in a 2026 clipboard-tool roundup as remote management (files, mirroring, SMS, remote control) that routes through the vendor’s servers and is not end-to-end encrypted by default. That page does not say the iOS app reads `UIPasteboard`. — [pastehere roundup](https://pastehere.app/best-clipboard-sync-tools).

### Inferences
- Commercial “iPhone managers” on Windows solve a different problem (photos, backups, app containers). They are not evidence that a non-jailbroken Windows PC can see `UIPasteboard` without either a developer service or a companion app.
- A practical image path that does not depend on iOS 27 mirroring: user saves or shares the image, then AFC/DCIM or a share-sheet upload moves the file. That loses “I copied it but did not save it”.
- The other direction for images, without iOS 27: companion app writes `UIPasteboard` image data, or the user drops a file into Files via the existing file-transfer plan. HID cannot carry the image.
- Rich text (fonts, RTF, HTML) is not preserved by any PC path reviewed except Universal Clipboard between Apple devices, which Porthole’s hosts cannot join. The CoreDevice client flattens to UTF-8 plus one bitmap.

### Gaps
- iTools, the Apple Devices app (Microsoft Store successor to iTunes), and AirDroid’s current iOS clipboard behavior were not confirmed from those vendors’ own 2026 manuals. Absence from iMazing’s feature list is reasonably strong. Absence for the others is “not found”, not a proof they lack a clipboard button.
- No size limits (pixels, bytes, or video duration) were found for Universal Clipboard or for `UIPasteboard`.
- Not checked: whether iOS 26’s pasteboard still round-trips HEIC, or whether Windows’ clipboard accepts HEIC without conversion. pymobiledevice3 already converts JPEG→PNG for the browser path; a native Windows clipboard write would have to pick a format Windows accepts (PNG or DIB are the safe choices; that is an inference from Windows clipboard practice, not from an Apple doc).

## What is impossible without a jailbreak, and what a personal tool can do on the owner’s phone

### Takeaway
Without a jailbreak, no Windows or Linux program can silently read or write the iPhone pasteboard through AirPlay, HID, or AssistiveTouch, and classic lockdown file services cannot either. What the owner can do, on a phone they unlock themselves, is: keep typing text with Alt+V; run a personal foreground app or Shortcut that reads and writes the pasteboard under iOS 16 paste rules; transfer saved files with AFC or the share sheet; and, if Developer Mode and a new enough DDI expose it, call `com.apple.coredevice.pasteboardservice` over USB. None of those require a jailbreak. The seamless system clipboard Windows wants is an EU feature Apple scheduled for fall 2027, not something iOS 26.6.1 already offers.

### Cited Findings
- Foreground-only reads since iOS 9, paste confirmation since iOS 16, and no API to query Allow/Deny: an app the user did not open cannot sit in the background and harvest copies. — [OWASP](https://mas.owasp.org/MASTG-KNOW-0083); [UIPasteControl](https://developer.apple.com/documentation/uikit/uipastecontrol); [Stack Overflow, 2025-12-13](https://stackoverflow.com/questions/79846681/how-to-check-paste-from-other-apps-pasteboard-permission-status).
- Get Clipboard is explicitly unsupported in the background. — [ScPL](https://docs.scpl.dev/actions/getclipboard).
- AFC, installation proxy, and house arrest are file and app services. The pasteboard service is a separate CoreDevice service that appears only when the mounted DDI provides it. — [python-api.md](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/python-api.md); [issue 1744](https://github.com/doronz88/pymobiledevice3/issues/1744); [pasteboard_service.py](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/remote/core_device/pasteboard_service.py).
- Developer Mode is an Apple setting the user turns on, with a security warning, a restart, and a passcode. It is how locally installed development apps are allowed to run. It is not described as a jailbreak. — [Apple Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device).
- Universal Clipboard’s device list stops at Mac, iPhone, iPad, and Vision Pro. — [Apple Support 108046, 2026-03-17](https://support.apple.com/en-us/108046).
- The Windows clipboard work Apple described is not shipping in November 2026. Target is fall 2027, with per-accessory consent, reported as EU-only. — [9to5Mac, 2026-08-03](https://9to5mac.com/2026/08/03/apple-plans-to-open-iphone-clipboard-access-to-windows-pcs/); [The Verge, 2026-08-04](https://www.theverge.com/tech/975020/apple-windows-pc-copy-paste-eu).

### Inferences
- A personal Porthole build can legally follow the same developer path Xcode uses on a device the owner pairs and unlocks: Trust This Computer, Developer Mode, mount the DDI, talk to services the image advertises. That is ordinary device-owner development, not a jailbreak and not a service for other people’s phones. Each extra phone would still need its own trust prompt and Developer Mode opt-in.
- A personal sideloaded companion is the same kind of development-signed app. It should expect the paste prompt (or a one-time Allow) and it should not expect to run a clipboard watcher while the user is in other apps, unless the owner also enables a keyboard extension and accepts that limitation as a product choice.
- Shipping a silent background reader would require either a future Apple accessory API (not available, and described as consent-gated) or a jailbreak. There is no third “private lockdown pasteboard” service in the pymobiledevice3 service map.
- For the implementation plan, the realistic matrix on iOS 26.6.1 is:
  - PC text → focused field: keep Alt+V (ASCII, US layout, no images, not the pasteboard).
  - PC text or image → iOS pasteboard, and iPhone copy → PC: try `PasteboardService` after `auto-mount` and see if 26.6.1 advertises it. If it does not, this path waits for iOS 27 or a DDI that contains the daemon.
  - Images and non-ASCII text that must work regardless: a small companion or Shortcut plus local HTTP, foreground only, with the system paste prompt or share sheet.
  - Do not plan on LetsView-style AirPlay, AssistiveTouch, or Universal Clipboard for a Windows or Linux host.

### Gaps
- This pass did not open Apple’s current developer-program license, so it does not quote a clause that “personal use is permitted”. The supported mechanism (development signing, Developer Mode, trust) is documented; a legal conclusion beyond that is not.
- No test on iOS 26.6.1, on an iPhone 14 Pro, or from an Ubuntu VM was done. The single iOS 26 datapoint is a third-party report for 26.2 on macOS with DDI 27A5194q.
- Jailbreak-only clipboard tweaks were not researched beyond noting they are unnecessary for the supported paths above. Low-quality pages advertising jailbreak clipboard apps were not used as technical sources.
